# [PerfLab #01] 5만 개 항목 검색 자동완성, 키워드 하이라이트까지 타이핑을 따라가려면? — 실험 계획

## 상황

쇼핑 앱이나 연락처 앱의 검색 화면이다. 상품 5만 개를 기기 안에 들고 있고, 사용자가 글자를 입력할 때마다 결과 목록이 바로 바뀐다.
각 행에서는 검색어와 일치한 부분을 강조한다. 예) 검색어 "하하" → **하하**이라다

입력은 1초에 10자 안팎으로 빠르게 들어온다. 한 글자마다 5만 개를 다시 거르고, 보이는 행마다 일치 위치를 찾아 강조 문자열을 만들어야 한다.

## 요구사항

- 화면: 위쪽 검색 입력창, 결과 개수, 결과 목록(상품 이름 한 줄).
- 검색어가 비어 있으면 결과는 없다.
- 검색어를 **부분 문자열로 포함**한 상품만 보여준다. 영문 대소문자는 구분하지 않는다. 결과는 상품 id 순서다.
- 결과 개수에 제한을 두지 않는다. 일치한 상품을 모두 목록에 넣는다 (목록은 스크롤할 수 있다).
- 이름 안의 **모든** 일치 위치를 굵게, 강조 색으로 표시한다. 일치 위치는 겹치지 않게 왼쪽부터 찾는다.
- 결과 형태는 `SearchMatch(productID, highlights: [Range<Int>])`이고, 위치는 UTF-16 오프셋이다. 모든 Stage가 같은 결과를 낸다.

## 예상 병목

### 사용자 예측

- **어떤 느림을 먼저 느낄까:** "글자가 늦게 찍힌다. 갱신이 늦는다. 검색와 후보 리스트 싱크가 순간적으로 안 맞는다."
- **처음 만든다면 어떻게 만들까 (거르는 위치, 하이라이트 시점):** "잘 모르겠어"
- **"하" → "하하"일 때 앞 결과를 활용할 방법:** "잘 모르겟어"

### 가설

1. **메인 스레드 필터링 (가장 큰 병목):** 입력마다 5만 개 이름을 `lowercased()`로 새로 만들고 `contains`로 훑는다.
   Mac에서 Stage 0 방식의 필터만 따로 돌려 본 참고값이 검색어당 약 53ms였다 (정식 측정 아님).
   입력 간격 100ms의 절반 이상을 메인 스레드가 쓰게 되어, 입력창 갱신과 스크롤이 함께 밀릴 것이다.
   사용자 예측의 "글자가 늦게 찍힌다"가 이 현상이다.
2. **하이라이트 위치 계산:** `range(of:options:)`는 `String.Index`로 문자를 하나씩 따라가고, 결과를 `NSRange`로 바꾸려면 UTF-16 오프셋으로 다시 세어야 한다.
   보이는 행마다(약 15~20개) 반복되므로 1보다는 작지만 스크롤할 때마다 생긴다.
3. **결과 적용:** 결과가 수천~2만 개라 목록 데이터를 통째로 바꾸는 비용도 있다. SwiftUI `List`가 2만 개 id를 비교하는 비용은 UIKit과 차이가 날 수 있다.
4. **"싱크가 안 맞는다":** 작업을 백그라운드로 옮기는 순간 생기는 문제다. 늦게 끝난 이전 검색어의 결과가 최신 결과를 덮으면 입력창과 목록이 어긋난다.
   Stage 1에서 취소와 순서 보장으로 다룬다.

## 시나리오

| 항목 | 값 |
|---|---|
| Seed | `Scenario.seed` |
| 데이터 규모 | 상품 5만 개 (`Scenario.productCount`). 이름은 브랜드 + 수식어 1~3개 + 품목 + 모델명(50%), 영문과 완성형 한글 |
| 갱신 주기 / 조작 | 100ms마다 한 글자 입력 또는 삭제 (`Scenario.keystrokeInterval`, `Scenario.typingScript` 62단계 반복) |
| Warm-up / 측정 시간 | 2s / 10s |

**Benchmark 모드 자동 재생 방식**

- `Scenario.typingScript`의 검색어를 차례로 입력창에 넣는다. 단어를 한 글자씩 입력한 뒤 한 글자씩 지우고, 8개 단어를 끝까지 돌면 처음부터 반복한다.
  - 입력 단어: 무선, 보조배터리, pro, 하하, SPEAKER, 미니 선풍기, 스마트, air
  - 단계별 결과 수는 213~22,238개다 (예: "a" 22,238개, "하하" 11,490개, "미니 선풍기" 213개).
- k번째 입력은 **재생 시작 시각 + k × 100ms**에 넣는다. 메인 스레드가 막혀 늦어지면 늦은 대로 바로 넣고 건너뛰지 않는다.
  모든 Stage가 같은 순서로 같은 검색어를 받게 하고, 화면에 얼마나 늦게 반영됐는지를 `inputDelay`로 잰다.
- 한글은 자모 조합(ㅎ → 하 → 핳 → 하ㅎ → 하하) 없이 완성된 글자 단위로 넣는다. 조합 중 검색은 이번 범위에서 뺀다.
- 목록은 자동 스크롤하지 않는다. 결과가 바뀔 때 화면에 보이는 첫 행들의 하이라이트가 매번 새로 그려진다.

## 측정 지표

- 공통: FPS (avg/min), Hitch (count, ms/s), CPU (avg/peak), Memory (avg/peak), Threads (peak)
- 주제별 커스텀 지표:

| 이름 | 단위 | 측정 위치 | 의미 |
|---|---|---|---|
| `indexBuildTime` | ms | 화면을 만들 때 검색 준비 작업의 시작 → 끝 | 검색 전에 한 번 드는 준비 비용. S0, S1은 준비 작업이 없어 0 |
| `inputDelay` | ms | 입력 예정 시각 → 그 입력을 처리한 뒤 첫 프레임이 화면에 나갈 시각 (`context.afterNextFrame`) | 입력이 화면에 얼마나 늦게 반영됐나 ("글자가 늦게 찍힌다"). 렌더 서버(GPU) 단계의 지연은 포함하지 않는다 |
| `resultLatency` | ms | 입력 시점 → 그 검색어의 결과를 목록 데이터에 적용한 시점 | 결과가 얼마나 늦게 갱신됐나 ("갱신이 늦는다") |
| `filterTime` | ms | 필터링(+ 해당 Stage가 미리 계산하는 하이라이트) 작업의 시작 → 끝 | 실행 스레드와 관계없이 검색 한 번에 드는 계산량 |
| `skippedResults` | % | 결과를 적용할 때 (적용 안 됨 100 / 적용됨 0) | 다음 입력에 밀려 화면에 한 번도 나오지 못한 검색어 비율 |
| `searchMemory` | MB | 결과를 적용할 때 | 검색을 위해 들고 있는 자료구조의 크기 추정치: 결과 배열 + 미리 계산한 일치 위치 + 인덱스 + 결과 스택. 상품 배열은 모든 Stage가 같으므로 뺀다 |

- 시간 지표는 원래 하는 작업의 앞뒤에서 시각만 읽는다. `resultLatency`의 시작점은 입력이 들어온 순간(UIKit 입력 이벤트, SwiftUI 바인딩 set)이다.
- 대가 지표(`searchMemory`, `indexBuildTime`)는 모든 Stage가 기록한다.
- `searchMemory`는 자료구조를 만드는 반복문 안에서 원소 수만 더해 `원소 수 × MemoryLayout.stride`(문자열 사본은 UTF-16 길이 × 2바이트)로 계산한다.
  할당기 오버헤드는 빠지므로 추정치이고, 실제 상주 메모리는 공통 지표 `Memory`로 함께 본다. 해당 구조가 없는 Stage는 그 항목을 0으로 센다.
- 셀마다의 하이라이트 생성 시간은 지표로 남기지 않고 signpost `highlight`로 Instruments에서 본다. 셀마다 기록하면 기록 자체가 부하가 된다.
- signpost: `filter`, `highlight`, `applyResults`

## Stage 전략

| Stage | 전략 | 축 | 핵심 개념 | 기대 효과 | 대가 | 대가 지표 |
|---|---|---|---|---|---|---|
| S0 Naive | 입력마다 메인 스레드에서 `name.lowercased().contains(query.lowercased())`로 전체를 거르고, 셀을 그릴 때 `range(of:options: .caseInsensitive)`를 반복해 일치 위치를 찾아 강조 문자열을 만든다 | - | 동기 처리, `String.Index` | 기준점 | - | - |
| S1 Optimized | S0의 검색 코드(거르기 + 일치 위치)를 그대로 백그라운드 `Task`로 옮긴다. 새 입력이 오면 이전 Task를 취소하고, 최신 검색어의 결과만 적용한다. 셀은 계산된 위치로 강조 문자열만 만든다 | 동시성 | 메인 스레드 분리, 협력적 취소(`Task.checkCancellation`), 결과 순서 보장 | `inputDelay`가 크게 줄고 입력이 밀리지 않는다 | 계산량은 그대로이고 결과 전체의 위치를 미리 구하므로 CPU와 메모리는 오히려 늘 수 있다. 취소된 작업 비용, 결과가 입력보다 늦게 따라온다 | `CPU`, `filterTime`, `searchMemory`, `resultLatency`, `skippedResults` |
| S2 Advanced | 상품마다 소문자 이름의 UTF-16 배열을 한 번만 만들어 둔다. 검색어가 직전 검색어를 포함하면 직전 결과 안에서만 거르고, 지울 때는 검색어별 결과 스택을 되돌린다. 일치 위치는 화면에 보일 행만 UTF-16 배열에서 바로 구한다 (백그라운드 + 취소는 S1 유지) | 자료구조와 알고리즘 | 전처리 인덱스, 증분 검색(검색 공간 줄이기), UTF-16 오프셋 직접 계산, 지연 계산 | `filterTime`과 CPU가 크게 줄고 `resultLatency`도 줄어든다 | 인덱스 메모리(5만 개 이름의 UTF-16 사본), 결과 스택 메모리, 첫 화면 전 인덱스 생성 시간, 코드 복잡도 | `searchMemory`, `Memory`, `indexBuildTime`, 정성: 코드 복잡도 |

축: 자료구조와 알고리즘, 값 타입과 참조 타입, 메모리, 동시성, 구조, 렌더링, I/O (`docs/GUIDE.md` 3절)

## 정합성 기준

- Stage마다 검색 로직을 UI와 분리된 타입으로 둔다 (`Stage0Search`, `Stage1Search`, `Stage2Search`). 화면 코드는 이 타입의 결과를 그리기만 한다.
- 테스트에 가장 단순한 기준 구현(`String.ranges(of:)` 기반)을 두고, 각 Stage의 결과 `[SearchMatch]`가 기준 구현과 같은지 확인한다.
  - `Scenario.typingScript`를 **순서대로** 모두 넣는다. 증분 검색(S2)이 입력과 삭제를 거쳐도 같은 결과를 내는지 확인하기 위해서다.
  - 대소문자 혼합("SPEAKER"), 공백 포함("미니 선풍기"), 한 이름에 여러 번 일치("하하"가 "하하상회 하하"에 2번)를 포함한다.
- S2는 하이라이트를 보이는 행에만 계산하므로, 테스트에서는 모든 결과 행에 대해 위치 계산 함수를 호출해 비교한다.
- 프레임워크 차이: SwiftUI의 `AttributedString`은 자기 인덱스만 받는다. 그래서 UTF-16 오프셋을 `String.Index`를 거쳐 한 번 더 바꾼다.
  프레임워크 API 때문에 생기는 비용이며, 모든 Stage에서 같은 방식을 유지한다.
