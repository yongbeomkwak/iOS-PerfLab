# [PerfLab #01] 5만 개 항목 검색 자동완성, 키워드 하이라이트까지 타이핑을 따라가려면? — 측정 결과

## 측정 환경

- **정식 결과:** iPhone 14 실기기 (iPhone14,7, iOS 26.6.1), 화면 최대 60fps. 2026-10-11 측정.
  - 측정 명령: `scripts/perflab measure 01-search-autocomplete-highlight --device "id=<기기 식별자>"`
  - 결과 원본: `results/iPhone14,7/stage<N>-<framework>.json`
- **참고용:** iPhone 17 Pro 시뮬레이터 (iPhone18,1, iOS 26.1), Mac에서 실행. 2026-10-11 측정.
  - 결과 원본: `results/iPhone18,1-simulator/stage<N>-<framework>.json`
- 빌드 구성: Release, warm-up 2초, 측정 10초, 조합마다 3회 반복의 중앙값, 빈 화면 baseline 포함
- 두 기기 모두 최대 60fps라, 기대 프레임 시간은 16.7ms이고 그 1.5배(25ms)를 넘으면 hitch로 센다. 120Hz(ProMotion) 조건은 측정하지 않았다.
- 아래 본문의 수치는 따로 밝히지 않으면 실기기 값이고, UIKit / SwiftUI 순서다.

**측정 이력.** 같은 날 두 번 측정했고, 이 문서는 두 번째 결과다.
- 첫 측정 뒤 코드 검증(`docs/VERIFICATION.md`)에서 측정 코드의 문제 두 가지가 나왔다. `searchMemory`가 S0 결과 배열을 실제 버퍼의 절반가량으로 셌고(0-13),
  `inputDelay`의 끝점이 메인 스레드가 막힌 뒤에는 이미 지나간 프레임 시각이 될 수 있었다(0-8). 둘을 고친 뒤 실기기와 시뮬레이터를 모두 다시 측정했다.
- 달라진 값: `searchMemory` S0 0.13 → 0.21MB / 0.14 → 0.22MB, S2 3.79 → 3.89MB. `inputDelay` S2 28.1 → 35.6ms / 29.8 → 46.5ms.
  그 밖의 지표는 측정 회차 사이의 차이 수준이다 (예: UIKit S0 hitch ratio 533.7 → 630.1ms/s, 3회 값 587.3~638.2).

**S1의 평균은 살아남은 검색만 담는다.** `filterTime`은 계산을 끝낸 검색만, `resultLatency`와 `searchMemory`는 화면에 적용된 검색만 기록한다. 계산 도중 취소된 검색은 어디에도 들어가지 않는다.
결과가 큰 검색어일수록 오래 걸려 밀려나므로, 절반이 버려진 S1의 세 값은 모두 실제보다 작다.
- `searchMemory`가 S0(0.21MB)보다 S1(0.14MB)이 작게 나온 것이 그 증거다. S1은 S0의 결과에 일치 위치까지 더 들고 있으므로 같은 검색어라면 더 작을 수 없다.
- 62단계를 취소 없이 모두 돌린 Mac 실험(code-verifier, 정식 측정 아님, 참고용)에서 S1의 `searchMemory` 평균은 0.449MB, 빠른 절반만 평균하면 0.135MB였다.
  같은 실험에서 S1의 검색 한 번은 S0의 1.41배(89.5ms / 63.5ms)였다. 결과 전체의 일치 위치를 미리 구하기 때문이다.
- 따라서 "S1은 계산량과 메모리가 S0과 같다"고 읽으면 안 된다. 실기기 표에서 S1의 대가로 확실히 말할 수 있는 것은 `skippedResults`와 CPU다.

## 분석

**S0: 메인 스레드가 막힌다.** 입력이 100ms마다 오고, 메인 스레드는 입력마다 5만 개 이름을 `lowercased()`로 새로 만들어 `contains`로 비교한다 (`filterTime` 64.7 / 69.6ms).
그동안 프레임을 그리지 못해 hitch ratio가 630.1 / 778.2ms/s, FPS avg가 23.0 / 12.0으로 떨어진다.
SwiftUI가 더 나쁘다. 거르는 시간은 비슷한데 `inputDelay`가 159.6ms로 입력 간격(100ms)을 넘는다.
입력 하나를 처리하는 메인 스레드 작업이 거르기 외에도 더 있어, 다음 입력이 올 때까지 끝나지 못하고 밀려 쌓인 것이다. 그 추가 작업이 무엇인지는 Instruments로 확인하지 않았다.

**S1: 메인은 비었지만 일은 줄지 않았다.** 같은 계산을 백그라운드로 옮기자 hitch가 두 프레임워크 모두 0, FPS가 60이 됐고 `inputDelay`가 33.2 / 32.6ms로 내려갔다.
CPU는 줄지 않았다 (85.3 / 87.3%, peak 102.5 / 101.3%로 코어 하나를 다 쓴다).
가장 큰 대가는 `skippedResults` 51 / 54%다. **입력한 검색어의 절반 이상이 결과를 한 번도 보여 주지 못했다.**
검색 한 번이 입력 간격 100ms 안에 끝나지 못하면 다음 입력에 취소되기 때문이다. 기기가 조금만 느려져도 한계선을 넘는 검색어가 늘어나는 구조다.

**S2: 일 자체를 줄였다.** 인덱스로 이름 변환이 사라지고 비교가 숫자 배열 비교가 되면서 `filterTime`이 1.82 / 0.87ms가 됐다. CPU는 31.0 / 36.9%로 S1의 절반 이하이고, 버려지는 검색어가 없다(`skippedResults` 0%).
- `filterTime` 평균은 경로가 섞인 값이다. 스크립트 62단계 중 23단계(지우기)는 스택의 결과를 다시 쓰는 reuse라 계산이 없다. S1의 65ms와 평균끼리 비교하면 개선을 부풀린다.
- 빨라진 원인은 두 가지로 확인됐다 (VERIFICATION 0-10, 2-4). Foundation의 `contains`는 유니코드 글자 경계를 따지며 비교하고, 직접 짠 UTF-16 비교는 시작 위치의 98.1%를 첫 코드 단위 비교 한 번으로 거른다.
- 대가로 메모리가 늘었다. `searchMemory`가 0.21 → 3.89MB이고, 실제 `Memory` peak는 S0 대비 +3.1MB(UIKit), +4.6MB(SwiftUI)다. 준비 시간(`indexBuildTime`)은 49.2 / 41.5ms다.
- S1 대비 `Memory` peak 증가는 +6.5MB / +15.4MB로 `searchMemory` 차이보다 훨씬 크다. S1은 큰 결과가 화면에 적용되지 못해 메모리가 낮게 나온 것으로 보이며, 두 Stage의 차이를 인덱스 크기만으로 읽으면 안 된다.

**S2의 hitch: UIKit은 거의 없고 SwiftUI에 남았다.** UIKit 4.0ms/s(3회 값 4.0, 0.0, 13.8), SwiftUI 126.4ms/s(125.4, 126.4, 139.8)다.
- UIKit: 중앙값은 Apple 기준 양호(5ms/s 미만)이지만 3회 중 한 번은 13.8ms/s(hitch 10회)였다. S1의 0보다는 많다. 결과가 입력 5ms 뒤에 도착해 입력창 갱신과 목록 갱신이 같은 프레임에 들어가는 영향일 수 있으나 확인하지 않았다.
- SwiftUI: 3회 모두 hitch가 31~32회로 일정하다. 검색 로직은 UIKit과 같으므로 원인은 결과를 화면에 적용하는 쪽에 있다.
  UIKit의 `reloadData`는 행 정보를 다시 묻고 보이는 셀만 만든다. SwiftUI `List`도 보이는 행만 만드는 것은 확인했지만(행 클로저 호출이 결과 200개와 2만 개에서 같았다, VERIFICATION 0-22),
  결과가 통째로 바뀔 때 `List`가 내부에서 하는 일의 비용은 확인하지 못했다. 그 비용이 결과 크기에 비례해 프레임 예산을 넘긴다는 것이 가설이다.
- 같은 SwiftUI인 S1은 hitch가 0이었다. S1은 결과의 절반이 적용되지 못했고 적용된 것은 작은 결과 위주였다(`searchMemory` 0.14MB). S2는 모든 결과를 적용한다.
  즉 S2는 "검색이 빨라져서 드러난 다음 병목"을 보여 준다. Instruments로 확인하지 않은 가설이다.

**Threads peak.** 실기기에서는 모든 조합이 11~13개였다. 백그라운드 Task를 쓰는 S1, S2도 S0보다 스레드가 늘지 않았다. Swift Concurrency가 코어 수만큼의 공용 스레드 풀에서 작업을 돌리기 때문이다.

**편차 경고 (실기기).** UIKit S2의 Hitch count와 ratio(위 3회 값), SwiftUI S2의 FPS min(36.8, 44.7, 38.7)과 CPU peak(56.5, 46.3, 60.9)에 나왔다.
결론에 쓴 FPS avg, CPU avg, Memory, `skippedResults`, SwiftUI의 hitch ratio는 3회 값이 모여 있어 다시 측정하지 않았다. UIKit S2의 hitch는 "거의 없다"까지만 말한다.

**시뮬레이터는 비교 기준이 되지 못했다.** 사흘 전(2026-10-08, iOS 26.5 런타임)과 오늘(iOS 26.1 런타임)의 시뮬레이터 결과가 크게 달랐다.
S0 `filterTime`이 46.1 → 67.7ms, S1 `skippedResults`가 13 → 54%다. 거르는 코드는 같았다. 런타임 버전과 Mac의 상태가 달랐다는 것 외에 원인은 확인하지 않았다.
- 오늘의 시뮬레이터는 편차 경고가 15건(Threads peak 6건, UIKit S2 hitch 등)으로 실기기(4건)보다 훨씬 흔들렸다.
- 실기기와 다른 점도 남아 있다. UIKit S2의 hitch ratio가 시뮬레이터 48.7ms/s, 실기기 4.0ms/s다.
- 첫 시뮬레이터 측정만 보고 "S1에서 버려지는 검색어는 13% 정도"라고 결론 냈다면 틀렸을 것이다. 정식 결과를 실기기로 정한 이유다.

## Instruments 관찰

실기기에서는 Instruments로 확인하지 않았다. 다음 항목이 가설로 남아 있다.

- SwiftUI S2 hitch의 출처: Time Profiler나 SwiftUI instrument로 결과 적용 직후 메인 스레드가 `List` 갱신에 쓰는 시간, Animation Hitches로 hitch가 결과 적용 프레임에 몰리는지.
- SwiftUI S0에서 거르기 외에 메인 스레드를 막는 작업.
- S1, S2의 Memory 차이: Allocations로 목록이 들고 있는 행과 인덱스의 실제 크기.

아래는 시뮬레이터 Release 빌드를 `xctrace`의 Time Profiler로 10초씩 기록한 결과다 (참고용, 2026-10-08, 검증 조치 이전 코드).

- **S0 UIKit:** 메인 스레드 시간의 약 25%가 `lowercased()`, 약 45%가 `contains`(Foundation `StringProtocol.contains`), 약 14%가 CA commit이었다.
- **S1 vs S2 UIKit:** 메인 스레드 샘플(1ms 단위)이 S1 748 → S2 1,342개였다. `cellForRowAt`이 91 → 314샘플인데, 지연 하이라이트 계산(`Stage2Index.highlights`)은 1샘플뿐이었다.
  `UIFont.bold` getter(8 → 35), UIKit 내부 프레임처럼 S1과 같은 코드가 고르게 약 3배 느렸다. signpost 개수(applyResults 184 vs 200, highlight 2,184 vs 2,436)는 비슷해 일의 양은 같았다.
