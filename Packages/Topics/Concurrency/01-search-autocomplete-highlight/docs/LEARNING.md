### [Plan] 입력마다 5만 개를 거르고 강조하면 어디가 먼저 느려질까 (2026-10-07)

- **Q1.** 사용자가 처음 느끼는 "느림"은 어떤 모습이고, 원인은 코드의 어디쯤일까?
- **사용자 답변:** "글자가 늦게 찍힌다. 갱신이 늦는다. 검색와 후보 리스트 싱크가 순간적으로 안 맞는다."
- **Q2.** 처음 만든다면 거르는 코드를 어디서 실행하고, 하이라이트 위치는 언제 구할까?
- **사용자 답변:** "잘 모르겠어"
- **Q3.** "하" → "하하"처럼 한 글자 늘어날 때 앞 결과를 활용할 방법이 있을까?
- **사용자 답변:** "잘 모르겟어"
- **해설:**
  - 세 증상은 원인이 다르다. "글자가 늦게 찍힌다"는 입력창 갱신과 필터링이 같은 메인 스레드에 있어서 생긴다.
    "갱신이 늦는다"는 계산 자체가 오래 걸려서, "싱크가 안 맞는다"는 작업을 백그라운드로 옮긴 뒤 늦게 끝난 이전 결과가
    최신 결과를 덮을 때 생긴다. 그래서 지표도 `inputDelay`, `resultLatency`, `skippedResults`로 나눴다.
  - Q2: 대부분 처음에는 입력 이벤트 안(메인 스레드)에서 바로 거르고, 셀을 그릴 때 `range(of:)`로 위치를 찾는다. 이것이 Stage 0이다.
  - Q3: "하하"를 포함하는 이름은 반드시 "하"도 포함한다. 그래서 "하하"는 5만 개가 아니라 "하"의 결과 안에서만 찾으면 된다.
    검색 공간을 줄이는 이 아이디어(증분 검색)가 Stage 2의 핵심이다.
- **이해 확인 (계획 후):**
  - **Q.** 계획을 승인하는가? 일치 부분은 모두 강조할까, 첫 번째만 강조할까?
  - **사용자 답변:** "모두 가종" (모두 강조로 승인)
  - **Q.** 입력을 "이전 입력 처리 후 100ms"가 아니라 "재생 시작 + k × 100ms" 시각에 넣고, 늦으면 건너뛰지 않고 바로 넣는 이유는?
  - **사용자 답변:** "모르겠어"
  - **해설:** "처리 후 100ms"로 넣으면 느린 Stage일수록 같은 10초 동안 입력을 덜 받는다. 부하가 저절로 줄어
    느린 구현이 실제보다 좋아 보인다 (coordinated omission). 시각을 고정하면 모든 Stage가 같은 입력을 같은 시점에 받고,
    밀린 정도는 `inputDelay`로 따로 드러난다. 건너뛰지 않는 이유도 같다. 건너뛰면 Stage마다 처리한 검색어가 달라진다.
  - **사용자 제안:** "스택이 메모리를 쓴다는 대가가 있으면 이거는 측정지표에 포함되야할 것 같아, S0,S1에 비해 S2가 얼마나 늘었는지,
    트레이드 오프를 판단하기 위해. 이번 뿐만아니라 각 시나리오에 대가가 있다면 그건 반드시 측정치표에 포함되야해"
    → `searchMemory`, `indexBuildTime`을 대가 지표로 추가했다. 파이프라인 규칙으로도 반영했다 (PLAN.md "대가 지표" 열, advance 검사).
- **남은 궁금증:** 한글 자모 조합 중("핳")에는 직전 검색어 포함 관계가 깨진다. 이번 범위에서는 완성된 글자 단위로만 입력한다.
