### [Plan] 입력마다 5만 개를 거르고 강조하면 어디가 먼저 느려질까 (2026-10-07)

- **Q1.** 사용자가 처음 느끼는 "느림"은 어떤 모습이고, 원인은 코드의 어디쯤일까?
- **사용자 답변:** "글자가 늦게 찍힌다. 갱신이 늦는다. 검색와 후보 리스트 싱크가 순간적으로 안 맞는다."
- **Q2.** 처음 만든다면 거르는 코드를 어디서 실행하고, 하이라이트 위치는 언제 구할까?
- **사용자 답변:** "잘 모르겠어"
- **Q3.** "하" → "하하"처럼 한 글자 늘어날 때 앞 결과를 활용할 방법이 있을까?
- **사용자 답변:** "잘 모르겟어"
- **해설:**
  - 세 증상은 원인이 다르다. "글자가 늦게 찍힌다"는 입력창 갱신과 필터링이 같은 메인 스레드에 있어서 생긴다.
    "갱신이 늦는다"는 계산 자체가 오래 걸려서, "싱크가 안 맞는다"는 작업을 백그라운드로 옮긴 뒤 늦게 끝난 이전 결과가
    최신 결과를 덮을 때 생긴다. 그래서 지표도 `inputDelay`, `resultLatency`, `skippedResults`로 나눴다.
  - Q2: 대부분 처음에는 입력 이벤트 안(메인 스레드)에서 바로 거르고, 셀을 그릴 때 `range(of:)`로 위치를 찾는다. 이것이 Stage 0이다.
  - Q3: "하하"를 포함하는 이름은 반드시 "하"도 포함한다. 그래서 "하하"는 5만 개가 아니라 "하"의 결과 안에서만 찾으면 된다.
    검색 공간을 줄이는 이 아이디어(증분 검색)가 Stage 2의 핵심이다.
- **이해 확인 (계획 후):**
  - **Q.** 계획을 승인하는가? 일치 부분은 모두 강조할까, 첫 번째만 강조할까?
  - **사용자 답변:** "모두 가종" (모두 강조로 승인)
  - **Q.** 입력을 "이전 입력 처리 후 100ms"가 아니라 "재생 시작 + k × 100ms" 시각에 넣고, 늦으면 건너뛰지 않고 바로 넣는 이유는?
  - **사용자 답변:** "모르겠어"
  - **해설:** "처리 후 100ms"로 넣으면 느린 Stage일수록 같은 10초 동안 입력을 덜 받는다. 부하가 저절로 줄어
    느린 구현이 실제보다 좋아 보인다 (coordinated omission). 시각을 고정하면 모든 Stage가 같은 입력을 같은 시점에 받고,
    밀린 정도는 `inputDelay`로 따로 드러난다. 건너뛰지 않는 이유도 같다. 건너뛰면 Stage마다 처리한 검색어가 달라진다.
  - **사용자 제안:** "스택이 메모리를 쓴다는 대가가 있으면 이거는 측정지표에 포함되야할 것 같아, S0,S1에 비해 S2가 얼마나 늘었는지,
    트레이드 오프를 판단하기 위해. 이번 뿐만아니라 각 시나리오에 대가가 있다면 그건 반드시 측정치표에 포함되야해"
    → `searchMemory`, `indexBuildTime`을 대가 지표로 추가했다. 파이프라인 규칙으로도 반영했다 (PLAN.md "대가 지표" 열, advance 검사).

### [Stage 0] 메인 스레드에서 5만 개를 거르면 화면은 어떻게 될까 (2026-10-07)

- **Q (구현 전).** "a"를 입력하는 순간 5만 개를 거르는 동안, 다음 글자 "i"가 찍히는 것과 화면 다시 그리기에는 무슨 일이 생길까?
- **사용자 답변:** "filter 고차함수가 메인스레드에서 실행되면, i가 찍히는 main thread(UI)작업이 뒤로 밀려 행이 발생할 것 같아. / 화면이 다시그릴 때, 굉장히 CPU 사용률이 올라갈 것 같아."
- **Q (구현 전).** `$0.name.lowercased()`는 입력 한 번마다 몇 번 실행되고, 매번 무엇을 새로 만들까?
- **사용자 답변:** "잘모르겠어"
- **해설:**
  - 그리기도 메인 스레드에서 시작하므로, 거르는 약 47ms 동안 화면은 아예 그려지지 않는다. CPU가 오른다기보다 그리기 자체가 멈춘다.
  - `lowercased()`는 입력마다 5만 번 실행되고 매번 새 문자열을 만든다. 한글은 글자당 3바이트라 대부분 15바이트를 넘어 힙 할당이 생긴다.
    이름은 바뀌지 않는데 같은 결과를 계속 다시 만든다. Time Profiler에서 메인 스레드의 약 25%가 `lowercased()`, 약 45%가 `contains`였다.
- **Q (구현 후).** hitch ratio 약 500ms/s를 "입력 간격 100ms, 거르기 47ms"로 설명할 수 있을까? S1에서 백그라운드로 옮기면?
- **사용자 답변:** "100 + 47 < 500 인데 이 간극은 어디에서 발생한거야?" / "백그라운드로 옮기면 메인이 공간이 있으니 시간이 줄어들지 않을까?"
- **해설:**
  - hitch ratio는 입력 한 번이 아니라 **1초 동안의 합**이다. 1초에 입력이 10번 오고, 매번 메인 스레드가 약 48ms 막힌다.
    막힌 동안 나가야 할 프레임이 밀린 시간이 약 48ms씩, 10번이면 약 480ms/s다. 100ms는 더하는 값이 아니라 입력 간격이다.
  - 백그라운드로 옮기면 메인 스레드는 결과를 적용하는 일만 하므로 hitch ratio는 Baseline 쪽으로 내려갈 것이다.
    다만 거르는 계산량(`filterTime`)과 전체 CPU는 줄지 않는다. 일을 다른 스레드로 옮겼을 뿐이다.
- **사용자 질문:** "THR은 무슨 지표야?" → 프로세스의 스레드 수(최대값). `task_threads`로 0.5초마다 센다.
  S1에서 Swift Concurrency의 작업은 CPU 코어 수만큼만 스레드를 쓰는 풀에서 돌기 때문에, 작업이 많아져도 스레드 수가 크게 늘지 않는지 볼 수 있다.
- **사용자 질문:** "Hitch 판단은 뭐로하니?" → display link 콜백 간격이 기대 프레임 시간(targetTimestamp − timestamp)의 1.5배를 넘으면 hitch로 센다.
  넘은 만큼(간격 − 기대 시간)을 더해 녹화 시간으로 나눈 값이 hitch ratio(ms/s)다. Apple 기준으로 5ms/s 미만은 양호, 10ms/s 이상은 심각이다.
- **이해 확인:** 체크포인트 답변과 질문으로 진행
- **남은 궁금증:** S1에서 메인 스레드가 비면 hitch는 줄지만, 결과가 늦게 따라오는 `resultLatency`는 어떻게 변할까 → Stage 1에서 확인

### [Stage 1] 검색을 백그라운드로 옮기면 무엇이 좋아지고 무엇을 치를까 (2026-10-07)

- **Q (구현 전).** 계산량은 같은데 `inputDelay`는 왜 줄까? `resultLatency`는 줄까, 그대로일까, 늘까?
- **사용자 답변:** "백그라운드 전환되면서 연산이 메인스레드 흐름 다른 흐름으로 동시 진행해서 줄어드는 것, resultLatency 역시 줄어들 것 같아."
- **Q (구현 전).** 취소가 없으면 "보조배터리"를 100ms 간격으로 칠 때 백그라운드와 화면에 무슨 일이 생길까?
- **사용자 답변:** "Task가 굉장히 많이 생성될 것 같아. 화면은 어떻게 될지 모르겠어"
- **Q (구현 전).** 이 방법의 대가는 어떤 지표에 드러날까?
- **사용자 답변:** "CPU이지 않을까 싶어.. 백그라운드 흐름이 생기니"
- **해설:**
  - `inputDelay`가 주는 이유는 맞다. 메인 스레드가 47ms 거르기를 하지 않으니 글자를 넣은 직후 프레임이 바로 나간다.
    하지만 `resultLatency`는 줄지 않는다. 계산 자체는 그대로이고, 결과 전체의 위치를 미리 구하는 일, 코어 경합, 메인으로 돌아오는 대기까지 더해진다.
    일을 다른 스레드로 옮기면 기다리는 주체(메인 스레드)가 바뀔 뿐, 일의 양과 걸리는 시간은 줄지 않는다.
  - 취소가 없으면 1초에 10개의 검색이 쌓인다. Swift Concurrency는 코어 수만큼만 스레드를 쓰므로 스레드가 폭증하지는 않는다.
    대신 버려질 검색에 CPU를 쓰고, **끝나는 순서가 입력 순서와 다를 수 있다.** "보조"(결과가 적어 빠름)가 "보"보다 먼저 끝나면,
    늦게 끝난 "보"의 결과가 덮어써 입력창은 "보조"인데 목록은 "보"의 결과가 된다. 계획 때 예측한 "검색과 후보 리스트 싱크가 순간적으로 안 맞는다"가 이것이다.
  - S1은 두 장치로 막는다. 새 입력이 오면 이전 Task를 `cancel()`하고, 결과를 적용하기 직전에 `Task.isCancelled`를 확인한다.
    취소와 확인이 모두 메인 액터에서 차례로 실행되므로 그 사이에 끼어들 틈이 없다. 버전 번호나 락이 필요 없다.
    `cancel()`은 표시만 남기므로(협력적 취소), 계산 쪽도 `Task.checkCancellation()`으로 스스로 멈춘다.
  - 대가는 CPU가 맞다. 이유는 백그라운드 흐름이 생겨서가 아니라, 일의 양이 줄지 않았고 오히려 늘었기 때문이다.
    S0는 보이는 15~20행만 위치를 구했지만 S1은 결과 전체(최대 2만 개)의 위치를 미리 구한다. 그 값을 들고 있으니 `searchMemory`도 는다.
    따라잡지 못한 검색어는 화면에 나오지 못하고(`skippedResults`), 중간에 취소된 계산도 CPU에는 남는다.
- **시뮬레이터 참고값 (정식 측정 아님, 4초 1회):**
  - UIKit S0 → S1: inputDelay 64 → 3ms, hitch 480 → 0ms/s, CPU 53 → 66%, filterTime 46 → 59ms, resultLatency 47 → 59ms, searchMemory 0.12 → 0.21MB, skippedResults 0 → 5%
  - SwiftUI S0 → S1: inputDelay 63 → 21ms, hitch 567 → 64ms/s, CPU 64 → 78%, skippedResults 0 → 13%
- **지표 해석 주의 (stage-reviewer 지적 반영):**
  - `resultLatency`는 적용된 결과만 평균한다. 건너뛴 검색어의 지연은 빠지므로 반드시 `skippedResults`와 함께 읽는다.
  - `filterTime`은 취소 전에 끝난 검색이면 적용되지 않아도 기록한다 (버려진 긴 검색이 평균에서 빠지지 않게). 중간에 멈춘 검색의 비용은 CPU로 본다.
  - S1의 `filterTime`은 백그라운드 경과 시간이라 코어 경합과 스케줄링 지연을 포함한다. S0 대비 증가를 계산량 증가로만 읽지 않는다.
  - SwiftUI는 `onChange`가 같은 갱신 안의 입력을 하나로 묶을 수 있어, 제출되지 않은 검색어는 `skippedResults`에 잡히지 않는다 (S0 SwiftUI도 같은 구조).
- **Q (구현 후).** 결과를 적용하기 직전의 `guard !Task.isCancelled`가 늦게 끝난 옛 결과를 확실히 막을 수 있는 이유는? (`cancel()`과 확인 코드는 각각 어느 액터에서 실행될까)
- **사용자 답변:** "잘 모르겟어"
- **해설:**
  - `cancel()`을 부르는 `submit`과, 결과를 받아 확인하고 적용하는 Task 본문은 모두 **메인 액터**에서 실행된다.
    무거운 계산(`@concurrent search`)만 백그라운드로 갔다가, `await`가 끝나면 메인 액터로 돌아온다.
  - 메인 액터는 한 번에 한 작업만 실행한다. 그래서 "확인 → 적용"이 도는 동안 `submit`(취소)이 끼어들 수 없고, 둘 중 하나가 먼저 끝까지 실행된다.
    - 새 입력이 먼저 처리됐다면 옛 Task는 이미 취소 표시가 있어 확인에서 걸러진다.
    - 확인과 적용이 먼저 끝났다면 그 결과가 그 시점의 최신이고, 바로 다음 입력이 다시 덮는다.
  - 만약 확인을 백그라운드에서 하고 적용만 메인으로 보냈다면, 확인과 적용 사이에 새 입력이 끼어들 수 있어 옛 결과가 새 결과를 덮을 수 있다.
    "확인과 적용을 같은 직렬 실행 환경(액터)에 둔다"가 핵심이다. 그래서 버전 번호나 락이 필요 없다.
- **사용자 발견:** 앱을 직접 실행해 보니 Stage나 프레임워크를 바꾸면 HUD가 멈췄다. 전환 때 새 `WindowReader`의 start 뒤에 옛 뷰의 stop이 불려
  display link가 꺼지던 Shared 버그였다. `fix/hud-stops-on-switch`로 고쳐 main에 머지했다 (자동 측정은 전환하지 않아 결과에는 영향 없음).
- **이해 확인:** 순서 보장 질문은 "잘 모르겠다"로 답해 해설로 정리했다.
- **사용자 질문:** "보(입력) -> 보(계산) 이 떄 보조(입력)이 들어오면 보계산을 버린다는거야??"
  → 맞다. `cancel()`은 표시만 남기고, 계산 쪽이 다음 `checkCancellation()`에서 스스로 멈춘다.
  계산이 끝났지만 적용 전이면 `guard !Task.isCancelled`에서 버려진다. 이 두 경우가 `skippedResults`다.
  "보조"는 "보"의 결과를 이어받지 않고 5만 개를 처음부터 다시 거른다 (이어받는 것이 Stage 2의 증분 검색).
- **이해 확인 (최종):** "좋아 이해했어"
- **사용자 질문 (Stage 2 전):** "2개의 테스크가 열렸어, 근데 Task 캔슬은 어떻게 해당 테스크가 캔슬된건지 판단하는거야?"
  → 취소 표시는 Task마다 따로 있다. `searchTask.cancel()`은 그 핸들이 가리키는 Task 하나에만 표시를 남긴다.
  `Task.isCancelled`와 `Task.checkCancellation()`은 static이지만 "지금 이 코드를 실행 중인 Task"의 표시를 읽는다.
  런타임이 작업을 스레드에서 실행할 때 현재 Task를 함께 기록해 두기 때문이다. `await`로 부른 `@concurrent` 함수는
  새 Task가 아니라 같은 Task의 일부로 실행되므로, 그 안의 확인도 바깥 Task의 표시를 본다.
- **남은 궁금증:** S1은 메인을 비웠지만 계산량(`filterTime`)과 `resultLatency`는 그대로다. 계산 자체를 줄이는 것은 Stage 2(인덱스 + 증분 검색)의 몫이다.

### [Stage 2] 계산량 자체를 줄이려면 (2026-10-08)

- **사용자 질문 (구현 전):** "지금 우리는 5만개에 대한 데이터를 알고 있는건데, 만약 서버에서 받아온다고 했을 때, 이런 전처리 작업이 가능해?"
  → 가능하다. 목록 전체를 받아 앱에서 검색한다면(수만 건, 드물게 바뀜) 응답을 디코딩할 때 함께 인덱스를 만들고, 페이지 단위면 새 항목만 더한다.
  매번 다시 만들지 않으려면 디스크에 저장한다 (실무에서는 SQLite FTS, Core Spotlight 같은 시스템 인덱스). `indexBuildTime`이라는 대가는 그 시점으로 옮겨 갈 뿐이다.
  데이터가 너무 크거나 자주 바뀌면 서버가 인덱스를 들고 검색하고, 앱은 S1의 취소, debounce, 결과 캐시를 맡는다. 보이는 행만 하이라이트하는 것은 어느 쪽이든 통한다.
- **Q (구현 전).** 전처리 인덱스는 `lowercased()`(약 25%)와 `contains`(약 45%) 중 무엇을, 어떻게 줄일까?
- **사용자 답변:** "lowercased를 줄일 것 같은데"
- **Q (구현 전).** "보" → "보조" → "보조배"에서 증분 검색이면 확인하는 상품 수가 어떻게 변할까? 지울 때 스택이 없으면?
- **사용자 답변:** "증분 검색의 동작 원리를 모르다보니 잘 모르겠어"
- **Q (구현 전).** 대가는 `searchMemory`, `Memory`, `indexBuildTime` 중 어디에 드러날까?
- **사용자 답변:** "잘 모르겠어, searchMemory, Memory, indexBuildTime 각 3개의 역할을 모르겠어"
- **해설:**
  - 인덱스는 입력마다 5만 번 하던 `lowercased()`를 화면을 열 때 한 번으로 바꾼다. `contains`도 유니코드 글자 경계를 따지는 비교에서 숫자 배열(UTF-16) 비교로 가벼워진다.
  - "보조"를 포함하는 이름은 반드시 "보"도 포함하므로, "보조"는 "보"의 결과 안에서만 찾으면 된다 (검색 공간 줄이기).
    지울 때는 결과가 다시 커지므로 앞 결과 안에서 찾을 수 없다. 스택이 없으면 5만 개를 처음부터 다시 거른다. 스택은 "보조"의 결과를 꺼내 계산 없이 다시 쓴다.
  - 대가 지표: `indexBuildTime`은 미리 하는 시간, `searchMemory`는 기억해 두는 자료구조의 크기 추정치, `Memory`는 앱 전체 실제 메모리로 추정치를 교차 확인한다.
- **변경 요인 분해 (Mac 마이크로 측정, 정식 아님, 5회 중 최소값):**

  | 검색어 (결과 수) | S1식 거르기 | 검색어 소문자 변환만 루프 밖으로 | 인덱스 전체 훑기 |
  |---|---|---|---|
  | "a" (22,238) | 40.4ms | 41.6ms | 0.60ms |
  | "하하" (11,490) | 52.6ms | 51.3ms | 0.61ms |
  | "보조" (3,151) | 58.3ms | 57.4ms | 0.67ms |
  | "미니 선풍기" (213) | 62.9ms | 54.8ms | 0.65ms |

  - 검색어 소문자 변환을 루프 밖으로 빼는 것은 긴 검색어(15바이트 초과로 힙 할당)에서만 약 13% 효과다. 대부분의 효과는 인덱스(이름 변환 제거 + 숫자 비교)에서 나온다.
  - 증분 검색: "보"의 결과 6,328개 안에서 "보조"를 찾는 데 0.08ms (전체 훑기 0.67ms 대비 약 8배). 인덱스 생성은 약 25ms.
  - 인덱스만으로 이미 1ms 아래라, 이 데이터 규모에서는 증분 검색의 절대 이득이 작다. 데이터가 커질수록 차이가 벌어진다.
- **시뮬레이터 참고값 (10초 3회 중앙값, 정식 아님):**
  - UIKit S1 → S2: filterTime 58 → 0.7ms, resultLatency 59 → 2ms, CPU 69 → 15%, skippedResults 13 → 0%, searchMemory 0.34 → 3.79MB, Memory 평균 53.6 → 57.6MB, indexBuildTime 0 → 25ms, **hitch 0 → 74ms/s**, inputDelay 12 → 20ms
  - SwiftUI S1 → S2: resultLatency 61 → 5ms, CPU 77 → 24%, hitch 41 → 123ms/s
- **지표 해석 주의 (stage-reviewer 지적 반영):**
  - S2의 `filterTime`, `resultLatency`는 경로가 섞인 평균이다 (스크립트 62단계 = full 8 · narrow 23 · reuse 23 · 빈 검색어 8). "같은 일을 빨리 했다"와 "일을 안 했다"가 섞여 있다. 경로별 시간은 signpost `filter`의 메시지(full/narrow/reuse)로 본다.
  - 스택에는 화면에 적용된 결과만 쌓이므로, 느린 기기에서 결과가 밀리면 narrow 대신 full이 늘어난다.
  - `searchMemory`는 배열마다 힙 헤더 32바이트를 더해 S1과 S2를 같은 기준으로 맞췄다 (S2 인덱스는 이름마다 배열 5만 개).
  - 인덱스는 화면을 먼저 그린 뒤 백그라운드에서 만들고 warm-up 중에 끝난다. 그 CPU와 첫 검색 지연은 측정 구간 밖이고 `indexBuildTime`으로만 드러난다 (PLAN 문구를 이에 맞게 고침).
- **사용자 질문:** "Stage2에서 탐색을 부루트 포스 방식아니지 않아? incremental search라고 했잖아."
  → 둘 다 맞고, 층이 다르다. 증분 검색은 **어떤 상품을 확인할지**(검색 공간, `Stage2ResultStack.plan`)를 정하고,
  brute-force는 **상품 이름 하나 안에서 검색어를 찾는 방법**(`Stage2Index.firstMatch`)이다. 바깥 층에서 후보 수를 5만 → 수천으로 줄이고,
  안쪽 층에서는 남은 이름마다 단순 비교를 한다. S0/S1의 `contains`도 안쪽 층은 훑기이고, S2는 그 비교 대상을 숫자 배열로 단순하게 만들었다.
- **사용자 질문:** "안쪽 검색은 혹시 Trie는 방식으로 개선할 수 있니?"
  → 일반 Trie는 **앞부분(prefix)** 일치용이라 "이름 어디든 포함(contains)"인 이 검색에는 그대로 맞지 않는다 ("선풍기"는 찾지만 "풍기"는 못 찾음).
  - 단어 단위 Trie: 이름을 단어로 나눠 넣으면 단어 시작 일치만 찾는다. 결과가 S0과 달라져 공정한 비교 조건(같은 결과)을 깬다.
  - 접미사 Trie / 접미사 배열: 모든 접미사를 넣으면 포함 검색이 된다. 대신 노드 수가 이름 길이 합(약 100만 개 이상)에 비례해 메모리와 생성 시간이 크게 는다.
  - n-gram 역색인: 두 글자 조각마다 그 조각을 가진 상품 목록을 둔다. 실무 한글 검색에서 흔하다. 후보를 크게 줄이지만 마지막 확인 비교는 여전히 필요하다.
  - 이 규모(인덱스 훑기 약 0.6ms)에서는 얻을 시간이 작고 대가(메모리, 생성 시간, 복잡도)가 커서 이번 범위에서는 하지 않는다. SUMMARY의 "다음 개선" 후보로 남긴다.
- **hitch 증가 (원인 미확정, 가설):**
  - Time Profiler(UIKit, 10초): 메인 스레드 샘플 S1 748 → S2 1,342. 셀 수는 비슷한데(highlight signpost 2,184 vs 2,436) `cellForRowAt`이 91 → 314샘플이다.
    지연 하이라이트 계산 자체는 1샘플이고, 같은 코드(`UIFont.bold`, UIKit 내부)가 고르게 약 3배 느렸다.
  - 가설 (a): 전체 CPU 사용이 낮아지자 코어 클럭이 낮게 머물거나 효율 코어에 배치되어, 메인 스레드의 같은 일이 느려졌다. Mac에 CPU 부하를 걸자 UIKit hitch가 89 → 39ms/s로 줄었다 (진단용 실험).
  - 가설 (b): 결과가 입력 직후(약 2ms) 도착해 입력창 갱신과 목록 갱신이 한 프레임에 몰린다. S1은 약 60ms 뒤라 프레임이 나뉘었다. CPU 부하에도 그대로였던 SwiftUI(111ms/s)에 더 맞는다.
  - 결론은 실기기 측정과 Instruments(CPU 코어 배치)로 확인한 뒤 내린다. 확인되면 S2의 대가에 "목록 갱신이 입력 프레임에 몰림"을 추가한다.
- **Q (구현 후).** "보조배터리"를 다 치고 한 글자씩 지울 때 각 단계는 어떤 경로(full/narrow/reuse)를 탈까? 그 단계의 `filterTime`이 거의 0인데 "S2가 S1보다 100배 빠르다"고 말하면 안 되는 이유는?
- **사용자 답변:** "잘모르겠어"
- **해설:**
  - 칠 때: "보"는 스택이 비어 full, "보조"부터 "보조배터리"까지는 바로 앞 결과 안에서만 거르는 narrow다. 적용할 때마다 스택에 [보, 보조, 보조배, 보조배터, 보조배터리]가 쌓인다.
  - 지울 때: "보조배터"를 입력하면 맨 위 "보조배터리"는 "보조배터"에 포함되지 않아 꺼내 버리고, 그 아래 "보조배터"가 같은 검색어라 reuse다.
    "보조배" → "보조" → "보"도 같은 방식으로 모두 reuse다. 계산을 하지 않으니 `filterTime`이 거의 0이다.
  - reuse는 같은 일을 빨리 한 것이 아니라 **일을 하지 않은 것**이다. 스크립트 62단계 중 23단계(지우기 전부)가 reuse라 평균이 0 쪽으로 크게 끌려 내려간다.
    그래서 S1 58ms와 S2 0.7ms의 평균만 비교하면 개선을 부풀린다. 같은 일끼리 비교하려면 경로별로 본다 (full끼리: Mac 참고값 약 50ms → 0.6ms).
  - 같은 이유로 S2의 이득은 입력 패턴에 따라 달라진다. 지우기가 없고 매번 새 단어를 치는 사용자에게는 reuse가 없다.
