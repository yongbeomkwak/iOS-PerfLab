### [Plan] 시세가 들어올 때 무엇이 프레임을 잡아먹을까 (2026-10-12)

- **Q1.** 매초 시세가 들어올 때 프레임을 가장 많이 잡아먹는 일은? (a) 2만 개 모델의 값을 바꾸는 일 (b) 2만 개를 다시 정렬하는 일 (c) 셀 갱신과 깜빡임(UI)
- **사용자 답변:** "c번 프레임을 가장 많이 작아먹는건 UI 작업이라고 생각해서"
- **Q2.** 처음 만든다면 종목 모델을 어떻게 정의하고, 시세가 오면 화면을 어떻게 갱신할까?
- **사용자 답변:** "struct Quote으로 하고 reloadData를 하겠지?"
- **해설:**
  - Q2의 답을 그대로 Stage 0으로 삼았다. 후보를 낼 때는 S0 class → S1 struct였지만, 실무에서 처음 쓸 법한 코드가 struct라는 답을 따라
    S0 struct → S1 class(GUIDE의 "큰 struct → class" 처방) → S2 Struct of Arrays로 순서를 바꿨다.
  - Q1은 가설로 남기고 측정으로 확인한다. `reloadData()`는 보이는 셀 15개 안팎만 다시 그리므로 UIKit에서는 정렬(5만 개, 비교 약 80만 번)이 더 클 것으로 본다.
    SwiftUI는 예측하지 않았다. 같은 틱의 `tickTime`(모델)과 `reloadTime`(UI)을 비교한다.
- **사용자 질문:** "UI 갱신은 모든 Stage에서 왜 고정했는지 이유가 궁금해, 난 이 부분도 중요한 것 같은데?"
  - **답:** 한 Stage에서 모델과 UI를 함께 바꾸면 개선이 어느 쪽 덕분인지 가를 수 없어서 고정했다.
    다만 고정한 방식(순위 식별 + `reloadData`)이 이미 UI 비용이 적은 쪽이라, 그대로 두면 "UI는 병목이 아니다"라는 결론이 설계에 미리 들어간다는 문제가 있었다.
  - **결정:** (A) 이 주제는 모델에 집중하고, UI 비용은 `reloadTime` 지표로 따로 잰다. 결론은 "이 UI 방식에서 어느 쪽이 무거웠나"까지만 낸다.
    UI 갱신 전략(id 식별과 diff, 바뀐 행만 갱신)은 다음 주제로 다룬다. (B) UI를 Stage로 넣기, (C) Stage 4개는 고르지 않았다.

### [Plan] 계획 확인: 직전 순위를 쓰지 않는 이유 (2026-10-12)

- **Q.** S2에서 직전 틱의 순위를 출발점으로 쓰면 거의 정렬된 배열을 정렬하게 되어 빨라질 수 있는데, 왜 쓰지 않기로 했을까?
  (a) 결과가 Stage마다 달라질 수 있어서 (b) 메모리 배치가 아닌 다른 효과가 섞여서 (c) Swift `sort`는 거의 정렬된 입력에서도 빨라지지 않아서
- **사용자 답변:** "c"
- **해설:** 이유는 (b)다. 이 주제가 재려는 것은 "같은 계산을 메모리에 어떻게 배치해서 하느냐"의 차이다.
  S2에서 출발 순서까지 바꾸면 빨라진 만큼이 Struct of Arrays 덕분인지, 정렬할 일이 줄어든 덕분인지 가를 수 없다.
  (c)는 사실과 다를 가능성이 크다. 계획을 세우며 Mac에서 돌린 참고 실험(2만 개 `Int32` 순번 배열, `-O`, 정식 측정 아님)에서,
  우연히 **이미 다 정렬된** 입력을 다시 정렬했을 때 0.16~0.24ms, id 순서에서 정렬했을 때 1.5~2.1ms였다.
  거의 정렬된 입력(일부만 바뀐 경우)은 재지 않았으므로, 얼마나 빨라지는지는 확인하지 않았다.
  (a)는 등락률이 같으면 id 순으로 정하므로 출발 순서와 관계없이 결과가 같다.
- **이해 확인:** 계획 승인. 제목 "매초" → "실시간으로", 태그 `CopyOnWrite` → `class` 변경에 동의함
- **남은 궁금증:** 직전 순위를 이용한 증분 정렬은 Algorithms 카테고리의 후속 주제 후보다.

### [Stage 0] struct Quote를 sorted(by:)로 정렬하면 무엇이 복사될까 (2026-10-12)

구현 전:

- **Q1.** `sorted`가 새 배열을 만들며 `Quote`를 복사할 때, 6글자가 넘는 종목명(힙에 있는 문자열)은 어떻게 될까?
  (a) 내용이 통째로 복사된다 (b) 같은 저장 공간을 함께 가리키고 참조 카운트가 하나 는다 (c) struct라 참조 카운트와 무관하다
- **사용자 답변:** "b"
- **Q2.** `tickTime`(반영 + 정렬 + 집계) 중 정렬의 비율은? (a) 30% 미만 (b) 30~70% (c) 70% 이상
- **사용자 답변:** "c"
- **해설:**
  - Q1은 (b)다. Swift `String`은 UTF-8 15바이트 이하면 값 안에, 넘으면 힙에 둔다 (VERIFICATION 0-2 실험). 힙 문자열을 복사하면 저장 공간을 함께 쓰고 참조 카운트를 올린다 (0-3).
    struct라도 안에 힙을 가리키는 필드가 있으면 ARC가 생긴다. 다만 Mac 실험에서는 종목명이 모두 힙일 때와 모두 값 안일 때 정렬 시간이 비슷했고, 이전 배열 해제만 0.14ms → 0.27ms로 늘었다 (0-8). 실기기에서는 Time Profiler로 확인한다.
  - Q2는 Mac 참고값과 맞다. 틱당 약 9.9ms 중 정렬이 9.3ms였다 (0-9, 정식 측정 아님). 실기기 결과는 measure 단계에서 본다.

구현 중 문답:

- **사용자 질문:** "렌더 스레드와 메인 스레드는 다른거야?"
  - **답:** 다르다. 메인 스레드는 앱 안에서 뷰 코드, 레이아웃, Core Animation 커밋을 한다. 렌더 서버는 앱 밖의 시스템 프로세스로, 커밋된 레이어를 합성하고 Core Animation 애니메이션을 진행한다.
    크래시에서 본 것은 렌더 서버가 아니라 **앱 안의 SwiftUI 스레드**(`ViewGraphDisplayLink.displayLinkTimer(isAsyncThread:)` → `updateOutputsAsync`)였다. "렌더 스레드"라고 부른 것은 부정확했다.
    FPS, Hitch, `reloadTime`은 메인 스레드만 보고, CPU는 앱의 모든 스레드를 합친다. 렌더 서버는 다른 프로세스라 CPU에도 들어가지 않는다.
- **사용자 질문:** "SwiftUI의 비동기 스레드라는 개념이 내가 없어서 그런 것 같아.. 조금만 더 설명해줄 수 있니?"
  - **답:** `View`는 `@MainActor`라 `body`는 메인에서 돈다. 하지만 애니메이션은 매 프레임 값을 계산해야 해서, SwiftUI는 일부를 메인 밖 자기 스레드에서 처리할 수 있다 (크래시 스택이 근거, 언제 쓰는지는 공식 문서에 없다).
    메인 밖에서 불릴 수 있는 클로저에는 SDK가 `@Sendable`을 붙인다. `keyframeAnimator`의 `content`는 `@Sendable`이고 `keyframes`는 아니다.
    표시가 없는 `keyframes` 클로저를 Swift 6가 메인 소속으로 추론했는데 SwiftUI가 메인 밖에서 불러 격리 검사에 걸렸다 (VERIFICATION 0-27, 0-42). 그래서 `nonisolated` 함수로 뺐다.
    실무 규칙: SwiftUI API의 `@Sendable` 클로저 안에서는 메인 전용 상태를 만지지 않는다.

구현 후:

- **Q.** `sorted(by:)`는 틱마다 새 배열(120B × 5만 = 600만 바이트)을 만든다. S1에서 모델을 `class`로 바꾸면 이 새 배열은?
  (a) 생기지 않는다 (b) 여전히 생기지만 8바이트 참조라 40만 바이트로 준다 (c) 크기 그대로다
- **사용자 답변:** "b"
- **해설:** 맞다. `sorted(by:)`는 원소 타입과 상관없이 새 배열을 만든다 (0-6). class면 배열에는 객체를 가리키는 참조가 담기고, 객체는 힙에 그대로 있다.
  대신 참조를 복사할 때마다 참조 카운트를 바꾸고, 비교할 때마다 참조를 따라가야 한다. 이 비용이 줄어든 복사량을 상쇄할지가 Stage 1의 질문이다.
- **검증에서 걸린 것:** ❌ 3건(머리말이 집계 대상을 잘못 말함, `Sendable` 이유가 틀림, 측정 장치 주석이 계획 단계 내용), ⚠️ 중 재생 루프 중복(`Task.yield`는 취소돼도 예외를 던지지 않음)과 SwiftUI 크래시. 모두 조치했다.
- **이해 확인:** 정답을 골랐다. 추가 질문 없음
- **남은 궁금증:** `reloadTime` 구간에 UI 작업이 들어오는지는 측정 단계에서 실기기 Instruments로 다시 확인한다. UIKit과 SwiftUI는 메인 밖에서 하는 일의 범위가 달라 프레임워크 간 비교는 조심해서 해석한다.
- **사용자 질문:** "왜 참조가 8byte야?"
  - **답:** 참조는 객체가 놓인 메모리 주소이고, arm64는 주소를 64비트(8바이트)로 표현한다. 객체가 아무리 커도 주소 크기는 같다.
    Mac(arm64)에서 class 참조, 옵셔널 참조, `UnsafeRawPointer`, `Int`가 모두 8바이트였다 (옵셔널은 주소 0을 nil로 써서 공간이 더 들지 않는다).
    S1에서는 배열 칸이 120B → 8B로 줄지만, 객체마다 헤더(타입 정보 + 참조 카운트) 16B가 붙어 인스턴스는 136B다 (같은 필드 구성의 `class_getInstanceSize`, Mac).
    값을 읽으려면 주소를 따라 힙까지 가야 한다.

### [Stage 1] struct를 class로 바꾸면 정렬이 빨라질까 (2026-10-12)

구현 전:

- **Q1.** S1의 `sortTime`은 S0에 비해? (a) 확실히 줄어든다 (b) 비슷하다 (c) 오히려 늘어난다
- **사용자 답변:** "c 메모리는 줄어들지만, 힙에서 참조하는 비용이 크다"
- **Q2.** S1의 `summaryTime`(읽기만 하는 집계)은 S0에 비해? (a) 줄어든다 (b) 비슷하다 (c) 늘어난다
- **사용자 답변:** "b"
- **해설:**
  - 계획 때 Mac 프로토타입(5만 개, 필드 11개, 정식 아님)에서 틱당 S0 약 10ms, S1 약 18ms였다. Q1 예측과 같은 방향이다.
  - "메모리는 줄어들지만"은 정확하지 않다. 줄어드는 것은 정렬할 때 옮기는 바이트이고, 전체 메모리는 객체 헤더 때문에 오히려 늘 수 있다 (`modelMemory`로 확인).
  - Q2는 Mac 참고값을 나눠 재지 않아 측정 결과와 함께 해설한다.

구현 후 (2026-10-12 시작, 2026-10-15 마무리):

- **Q.** S0의 `applyUpdates`에는 retain/release가 없는데 S1에는 종목마다 한 쌍씩 생긴다. 이유는?
  (a) 꺼낸 참조를 지역 변수가 쓰는 동안 객체를 붙잡아 둬야 해서 (b) `Double` 필드를 바꿀 때마다 참조 카운트가 바뀌어서 (c) `final` 때문에
- **사용자 답변:** "a"
- **해설:** 맞다. 배열에서 꺼낸 참조를 지역 변수에 담으면 그 변수가 쓰이는 동안 객체가 해제되지 않도록 retain으로 카운트를 올리고, 끝나면 release로 내린다. `Double` 필드를 쓰는 것은 객체 안 메모리를 바꾸는 일이라 카운트와 무관하고(b), `final`은 호출 방식에 관한 것이다(c). Release 목적 파일에서 `applyUpdates`는 종목마다 retain/release가 있고 S0에는 없었다 (VERIFICATION 1-13).
- **이해 확인:** 정답을 골랐다. 이유 설명은 따로 받지 않았다.
- **남은 궁금증:** 틱당 5만 쌍의 retain/release가 실제로 CPU 지표에 얼마나 나타나는지는 측정 단계에서 확인한다.

### [Stage 2] Struct of Arrays는 왜 정렬을 빠르게 할까 (2026-10-15)

구현 전:

- **Q1.** S2가 정렬(`sortTime`)을 줄이는 이유는? (a) 옮기는 바이트가 줄어서 (b) 비교할 때 읽는 메모리가 작고 연속이라 캐시를 잘 써서 (c) 비교 함수 호출이 사라져서
- **사용자 답변:** "b"
- **Q2.** 대신 무엇을 대가로 치를까? (처음 질문에 "잘 모르겠어", 선택지로 좁혀 다시 물음: (a) 행을 만들려면 여러 배열에서 모아야 한다 (b) 필드를 추가하면 배열을 함께 늘리고 길이를 맞춰야 한다 (c) 정렬 결과를 화면에 보일 수 없다)
- **사용자 답변:** "잘모르겠어" → "b, 확실히 관리가 어려울 것 같고, 흠 메모리적으로도 뭔가 배열 개수가 늘어나는 것도 비용은 것 같네"
- **해설:**
  - (b)가 맞다. (a)도 대가다: 한 행을 그리려면 여러 배열에서 값을 모아야 한다. 정렬과 집계에는 이득이지만 행을 읽는 쪽은 불리해진다.
  - 메모리: 배열 11개의 헤더는 5만 종목에 비해 작다. 배열 수보다 객체 헤더(S1의 16B)와 구조체 패딩이 없다는 점, 순번 배열이 새로 생긴다는 점이 더 크다. `modelMemory`가 S0, S1보다 작아질 것이라는 것은 예상이고, 측정으로 확인한다.
