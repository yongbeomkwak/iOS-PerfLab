### [Plan] 시세가 들어올 때 무엇이 프레임을 잡아먹을까 (2026-10-12)

- **Q1.** 매초 시세가 들어올 때 프레임을 가장 많이 잡아먹는 일은? (a) 2만 개 모델의 값을 바꾸는 일 (b) 2만 개를 다시 정렬하는 일 (c) 셀 갱신과 깜빡임(UI)
- **사용자 답변:** "c번 프레임을 가장 많이 작아먹는건 UI 작업이라고 생각해서"
- **Q2.** 처음 만든다면 종목 모델을 어떻게 정의하고, 시세가 오면 화면을 어떻게 갱신할까?
- **사용자 답변:** "struct Quote으로 하고 reloadData를 하겠지?"
- **해설:**
  - Q2의 답을 그대로 Stage 0으로 삼았다. 후보를 낼 때는 S0 class → S1 struct였지만, 실무에서 처음 쓸 법한 코드가 struct라는 답을 따라
    S0 struct → S1 class(GUIDE의 "큰 struct → class" 처방) → S2 Struct of Arrays로 순서를 바꿨다.
  - Q1은 가설로 남기고 측정으로 확인한다. `reloadData()`는 보이는 셀 15개 안팎만 다시 그리므로 UIKit에서는 정렬(5만 개, 비교 약 80만 번)이 더 클 것으로 본다.
    SwiftUI는 예측하지 않았다. 같은 틱의 `tickTime`(모델)과 `reloadTime`(UI)을 비교한다.
- **사용자 질문:** "UI 갱신은 모든 Stage에서 왜 고정했는지 이유가 궁금해, 난 이 부분도 중요한 것 같은데?"
  - **답:** 한 Stage에서 모델과 UI를 함께 바꾸면 개선이 어느 쪽 덕분인지 가를 수 없어서 고정했다.
    다만 고정한 방식(순위 식별 + `reloadData`)이 이미 UI 비용이 적은 쪽이라, 그대로 두면 "UI는 병목이 아니다"라는 결론이 설계에 미리 들어간다는 문제가 있었다.
  - **결정:** (A) 이 주제는 모델에 집중하고, UI 비용은 `reloadTime` 지표로 따로 잰다. 결론은 "이 UI 방식에서 어느 쪽이 무거웠나"까지만 낸다.
    UI 갱신 전략(id 식별과 diff, 바뀐 행만 갱신)은 다음 주제로 다룬다. (B) UI를 Stage로 넣기, (C) Stage 4개는 고르지 않았다.

### [Plan] 계획 확인: 직전 순위를 쓰지 않는 이유 (2026-10-12)

- **Q.** S2에서 직전 틱의 순위를 출발점으로 쓰면 거의 정렬된 배열을 정렬하게 되어 빨라질 수 있는데, 왜 쓰지 않기로 했을까?
  (a) 결과가 Stage마다 달라질 수 있어서 (b) 메모리 배치가 아닌 다른 효과가 섞여서 (c) Swift `sort`는 거의 정렬된 입력에서도 빨라지지 않아서
- **사용자 답변:** "c"
- **해설:** 이유는 (b)다. 이 주제가 재려는 것은 "같은 계산을 메모리에 어떻게 배치해서 하느냐"의 차이다.
  S2에서 출발 순서까지 바꾸면 빨라진 만큼이 Struct of Arrays 덕분인지, 정렬할 일이 줄어든 덕분인지 가를 수 없다.
  (c)는 사실과 다를 가능성이 크다. 계획을 세우며 Mac에서 돌린 참고 실험(2만 개 `Int32` 순번 배열, `-O`, 정식 측정 아님)에서,
  우연히 **이미 다 정렬된** 입력을 다시 정렬했을 때 0.16~0.24ms, id 순서에서 정렬했을 때 1.5~2.1ms였다.
  거의 정렬된 입력(일부만 바뀐 경우)은 재지 않았으므로, 얼마나 빨라지는지는 확인하지 않았다.
  (a)는 등락률이 같으면 id 순으로 정하므로 출발 순서와 관계없이 결과가 같다.
- **이해 확인:** 계획 승인. 제목 "매초" → "실시간으로", 태그 `CopyOnWrite` → `class` 변경에 동의함
- **남은 궁금증:** 직전 순위를 이용한 증분 정렬은 Algorithms 카테고리의 후속 주제 후보다.
