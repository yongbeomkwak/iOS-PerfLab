# [PerfLab #02] 수만 개 종목을 실시간으로 갱신하는 시세 대시보드, 모델 타입과 메모리 배치가 얼마나 차이를 만들까? — 실험 계획

## 상황

증권 앱의 "전 종목 등락률 순위" 화면이다. 종목 5만 개를 기기 안에 들고 있고, 서버에서 1초에 4번 시세 묶음이 들어온다.
묶음마다 종목 5천 개의 가격이 바뀌고, 목록은 등락률 순으로 다시 정렬된다. 위쪽에는 상승·하락·보합 종목 수가 나온다.
가격이 바뀐 행은 오르면 빨강, 내리면 파랑으로 잠깐 깜빡인다.

틱마다 하는 일은 세 가지다.

1. **반영**: 바뀐 종목 5천 개의 가격, 고가, 저가, 거래량을 고친다.
2. **정렬**: 5만 개 전체를 등락률 순으로 다시 줄 세운다.
3. **집계**: 5만 개를 훑어 상승·하락·보합 종목 수를 센다.

이 주제는 **같은 세 가지 일을 모델을 어떤 타입으로, 메모리에 어떻게 배치해서 하느냐**에 따라 비용이 얼마나 달라지는지를 잰다.
처방은 실제 증권 앱의 구현을 보고 고른 것이 아니라 일반적인 CS 지식에서 고른 가설이다. 이 상황에서 정말 효과가 있는지를 측정으로 확인한다.

## 요구사항

- 화면: 위쪽 집계 한 줄(상승 N · 하락 N · 보합 N), 아래 종목 목록.
- 행: 순위, 종목명, 종목 코드, 현재가, 등락률(%). 행 높이는 고정이다.
- 정렬: 등락률 내림차순. 등락률이 같으면 id 오름차순이다.
  등락률은 `(현재가 - 전일 종가) / 전일 종가`이고 `Double`로 계산한다.
- 집계: 등락률 > 0 상승, < 0 하락, = 0 보합.
- 깜빡임: **직전 틱에 가격이 바뀐 종목**이 화면에 보이면, 직전 가격보다 올랐으면 빨강, 내렸으면 파랑으로 0.3초 동안 배경을 칠했다가 지운다.
- 틱 하나의 결과는 `순위별 종목 id 배열 + 집계 + 종목별 표시 값`이고, 모든 Stage가 같은 결과를 낸다.

### UI 갱신 방식은 모든 Stage에서 고정한다

이 주제의 실험 변수는 모델 타입과 메모리 배치뿐이다. 그래서 화면 갱신 방식은 모든 Stage가 같다.

- 행은 **순위(위치)로 식별**한다. n번째 행은 "지금 n등인 종목"을 그린다. 종목 id로 식별하면 순위가 바뀔 때마다 5만 개의 이동을 계산하게 된다.
  그 비용은 백로그의 "SwiftUI `List` 갱신" 주제에서 따로 다룬다.
- UIKit: `UITableView`의 `reloadData()`를 틱마다 한 번 부른다. 다시 그리는 셀은 화면에 보이는 셀뿐이다.
- SwiftUI: `List`에 크기가 바뀌지 않는 `ForEach(0..<Scenario.quoteCount)`를 두고, 틱마다 바뀌는 값 하나로 보이는 행을 다시 그린다.
- 화면은 모델에서 `순위 → 표시용 행 값(QuoteRow)`과 집계만 받는다. Stage마다 다른 것은 이 값을 만들어 주는 모델 쪽이다.

고정한 이유와 한계:

- 한 Stage에서 모델과 UI를 함께 바꾸면, 개선이 어느 쪽 덕분인지 가를 수 없다. 그래서 UI는 실험 변수에서 뺀다.
- 고정한 방식(순위 식별 + `reloadData`)은 **이미 UI 비용이 적은 쪽**이다. id 식별과 diff, 이동 애니메이션처럼 UI 비용이 커지는 방식은 이 주제에서 재지 않는다.
  따라서 이 주제의 결과로 "시세 화면에서 UI는 병목이 아니다"라고 일반화하지 않는다. 결론은 "이 UI 방식에서 모델과 UI 중 어느 쪽이 무거웠나"까지다.
- UI 비용은 Stage로 바꾸지 않고 `reloadTime`으로 따로 잰다. UI 갱신 전략 자체는 다음 주제로 다룬다 (백로그의 "SwiftUI `List` 갱신", "채팅 리스트 업데이트").

## 예상 병목

### 사용자 예측

- **Q1. 시세가 들어올 때 프레임을 가장 많이 잡아먹는 일은? ((a) 모델 값 갱신 (b) 정렬 (c) 셀 갱신·깜빡임)**
  "c번 프레임을 가장 많이 작아먹는건 UI 작업이라고 생각해서"
- **Q2. 처음 만든다면 모델과 화면 갱신을 어떻게?** "struct Quote으로 하고 reloadData를 하겠지?"

### 가설

1. **정렬 (가장 큰 병목):** 틱마다 5만 개를 정렬하면 비교가 대략 n·log₂n ≈ 80만 번이다.
   Mac에서 Stage 0 방식(반영 + 정렬 + 집계)을 따로 돌려 본 참고값이 틱당 약 10ms였다 (5만 개, 필드 11개짜리 프로토타입, `-O`, 정식 측정 아님).
   120Hz 화면의 프레임 예산은 8.3ms이므로, 실기기에서는 틱마다 프레임을 1개 이상 넘길 것이다.
2. **반영과 집계:** 반영은 5천 번의 대입이라 정렬보다 훨씬 작을 것이다. 집계는 5만 번을 훑지만 비교 한 번씩이라 정렬보다 작다.
   다만 집계는 **필드 하나만 읽고 나머지는 건너뛰는 작업**이라, 메모리 배치의 차이가 가장 순수하게 드러날 것이다.
3. **UI (사용자 예측 c):** `reloadData()`는 보이는 셀 15개 안팎만 다시 그리므로, UIKit에서는 모델 작업보다 작을 것으로 본다.
   SwiftUI는 `List`가 값 변경을 처리하는 비용을 확인하지 못해 예측하지 않는다. 같은 틱의 `tickTime`(모델)과 `reloadTime`(화면)을 나란히 비교해 확인한다.
4. **struct의 정렬 비용:** `struct Quote`는 필드가 12개(정수 2, 문자열 3, 실수 7)라 한 개가 120바이트다 (같은 필드 구성의 `MemoryLayout.stride`, Mac에서 확인).
   정렬은 원소를 옮기며 줄을 세우므로, 원소가 클수록 옮기는 바이트가 늘어난다. Stage 1, 2는 이 비용을 다른 방식으로 줄여 본다.

## 시나리오

| 항목 | 값 |
|---|---|
| Seed | `Scenario.seed` |
| 데이터 규모 | 종목 5만 개 (`Scenario.quoteCount`). 종목명은 한글 4~9글자(우선주 10%는 뒤에 " 우"), 6자리 종목 코드, 업종 10종 |
| 갱신 주기 / 조작 | 250ms마다 묶음 하나 (`Scenario.tickInterval`). 묶음마다 서로 다른 종목 5천 개의 새 가격과 거래량 증가분 (`Scenario.updatesPerTick`). 미리 만든 40개 묶음을 반복 (`Scenario.batches`) |
| Warm-up / 측정 시간 | 2s / 10s |

규모를 정한 근거:

- **5만 개:** 실제 국내 상장 종목은 이보다 훨씬 적다. Stage 0에서 병목이 **분명히 드러나도록** 해외 종목과 ETF까지 담은 화면을 가정해 키웠다.
  Mac 참고값으로 2만 개는 틱당 약 3.5ms라 실기기에서도 프레임 예산 안에 들 수 있어서, 차이가 잘 보이지 않을 수 있다.
- **250ms:** 1초에 한 번이면 10초 측정에서 틱이 10번뿐이라 hitch 표본이 적다. 실시간 체결 화면을 가정해 1초에 4번으로 했다 (측정 구간에 40틱).
- **5천 개:** 가격이 바뀐 종목이 매 틱 보이는 행에도 들어오도록 했다 (10%). 반영 비용보다 정렬 비용이 주인공이 되는 비율이다.
- 새 가격은 직전 가격이 아니라 **전일 종가 기준**으로 정한다. 그래서 40개 묶음을 반복해도 가격이 한쪽으로 흘러가지 않는다. 가격 제한폭 ±30%를 지킨다.

**Benchmark 모드 자동 재생 방식**

- 화면이 뜨면 바로 틱을 시작한다. k번째 틱은 **재생 시작 시각 + k × 250ms**에 적용한다. 메인 스레드가 막혀 늦어지면 늦은 대로 바로 적용하고 건너뛰지 않는다.
  모든 Stage가 같은 순서로 같은 묶음을 받는다.
- 목록은 자동 스크롤하지 않는다. 등락률 상위 종목이 보이는 맨 위에 머문다. 매 틱 보이는 행의 값과 깜빡임이 바뀌어 화면이 계속 새로 그려진다.
- Interactive 모드도 같은 타이머로 틱을 적용한다. 사용자는 스크롤해서 다른 순위를 볼 수 있다.

## 측정 지표

- 공통: FPS (avg/min), Hitch (count, ms/s), CPU (avg/peak), Memory (avg/peak), Threads (peak)
- 주제별 커스텀 지표:

| 이름 | 단위 | 측정 위치 | 의미 |
|---|---|---|---|
| `tickTime` | ms | 틱 하나의 반영 시작 → 집계 끝 (메인 스레드) | 모델이 틱 하나에 쓰는 시간. 세 지표의 합이다 |
| `updateTime` | ms | 반영 시작 → 끝 | 5천 개 종목의 값을 고치는 시간 |
| `sortTime` | ms | 정렬 시작 → 끝 | 5만 개를 등락률 순으로 줄 세우는 시간 |
| `summaryTime` | ms | 집계 시작 → 끝 | 5만 개를 훑어 상승·하락·보합을 세는 시간 |
| `reloadTime` | ms | 모델 작업이 끝난 뒤 → 그 런루프 회차에서 화면 갱신(레이아웃, 셀 구성, SwiftUI 뷰 갱신, Core Animation 커밋)이 끝난 시점 | 틱 하나에서 화면을 갱신하는 데 쓴 메인 스레드 시간. 사용자 예측 (c)를 확인하는 지표다. 모든 Stage가 같은 UI라 Stage 간에 비슷해야 정상이다. 다만 셀을 구성하며 부르는 `row(at:)`(모델이 표시용 값을 만드는 비용)가 들어가므로, 그 비용이 다른 Stage는 조금 달라질 수 있다 |
| `tickLatency` | ms | 틱 예정 시각 → 그 틱을 적용한 뒤 첫 프레임이 화면에 나갈 시각 (`context.afterNextFrame`) | 시세가 화면에 얼마나 늦게 반영됐나. 모델 + 화면 갱신 + 다음 프레임까지 기다린 시간이 모두 들어간다. 렌더 서버(GPU) 단계는 포함하지 않는다 |
| `modelMemory` | MB | 틱마다 (값은 틱마다 같다. 측정을 시작할 때 지표가 초기화되므로 매번 남긴다) | Stage가 시세를 담으려고 들고 있는 구조의 크기 추정치 (아래 계산법) |

- 시간 지표는 원래 하는 작업의 앞뒤에서 시각만 읽는다.
- `reloadTime`의 끝점: 메인 런루프가 잠들기 직전(`beforeWaiting`)에 불리는 관찰자를 Core Animation 커밋보다 **늦은 순서**로 하나 걸어 시각을 읽는다.
  화면 갱신은 이 회차의 커밋 때 몰아서 처리되므로, 시작점(모델 작업 끝)부터 이 시각까지가 화면 갱신 시간이다. 관찰자는 시각만 읽으므로 원래 하지 않던 작업을 더하지 않는다.
  - **Stage 0에서 임시 출력으로 확인함 (2026-10-12, 시뮬레이터 iPhone 17 Pro, Debug):** `QuoteCell.configure`, `QuoteRowView.body`, `refresh()`의 시작과
    `reload()` 반환, 이 관찰자가 불리는 시각을 `print`로 출력하고 `simctl launch --console-pty`로 모아 틱마다 순서를 비교했다.
    UIKit은 틱마다 `cellForRowAt` 13번이 모두 이 구간 안에서 불렸다 (`reloadData()` 반환 후 → 관찰자 전). SwiftUI도 `QuoteRowView.body` 13~14번이 모두 이 구간 안에서 불렸다.
    임시 출력은 확인 뒤 지웠기 때문에 코드 검증에서는 재현되지 않았다 (VERIFICATION 0-15). 측정 단계에서 실기기 Instruments로 한 번 더 확인한다.
    Debug 시뮬레이터라 구간 길이는 참고하지 않는다.
  - **한계:** 이 관찰자는 메인 스레드가 **처음 한가해지는 순간**에 불린다. 그래서 그 사이 메인 스레드가 한 다른 일(애니메이션 프레임 처리, 다른 타이머)도 섞일 수 있다.
    위 실험에서 SwiftUI는 행 body가 시작 후 1ms 안에 끝났는데 관찰자는 8~15ms 뒤에 불렸다. 그 사이의 일(`List` 레이아웃, 커밋 등으로 추정)은 이 지표로 나눠 볼 수 없고 Instruments로 본다.
- 사용자 예측 (c)는 두 가지로 확인한다. ① 같은 틱의 `tickTime`과 `reloadTime` 중 어느 쪽이 큰가. ② 프레임워크가 같을 때 Stage 간 `tickTime` 차이만큼 Hitch가 달라지는가.
- `tickLatency`에는 모델, 화면 갱신, 다음 프레임 경계까지 기다린 시간이 모두 들어 있다. 사용자가 체감하는 지연이고, 원인을 나눠 보는 데는 위의 두 지표를 쓴다.
- `modelMemory` 계산법: 배열은 `capacity × MemoryLayout<원소>.stride`, 객체는 객체마다 `malloc_size`(할당기가 실제로 내준 크기)를 더한다.
  문자열 저장 공간은 모든 Stage가 `Scenario.seeds`의 문자열을 그대로 나눠 쓰므로 뺀다. 할당기의 관리 비용도 빠지므로 추정치이고, 실제 상주 메모리는 공통 지표 `Memory`로 함께 본다.
- 틱마다 새로 할당했다가 버리는 메모리(정렬 결과 배열 등)는 이 지표에 들어가지 않는다. Instruments의 Allocations로 확인한다.
- ARC(참조 카운트 증감) 비용은 따로 셀 수 없다. 실행 시간 지표에 섞여 나오고, Time Profiler에서 `swift_retain` / `swift_release`가 차지하는 비율로 확인한다.
- signpost: `applyTick`(틱 전체), `updateQuotes`, `sortQuotes`, `summarize`, `reloadRows`.

## Stage 전략

| Stage | 전략 | 축 | 핵심 개념 | 기대 효과 | 대가 | 대가 지표 |
|---|---|---|---|---|---|---|
| S0 Naive | `struct Quote`(필드 12개)를 종목 id 순서의 배열에 담는다. 틱마다 해당 칸의 값을 고치고, `sorted(by:)`로 등락률 순 **새 배열**을 만들고, 배열을 훑어 집계한다. 등락률은 계산 프로퍼티다 | - | 값 타입 배열, 정렬 시 원소 이동 | 기준점 | - | - |
| S1 Optimized | 모델을 `final class Quote`로 바꾼다. 나머지(배열 구조, 정렬, 집계)는 S0과 같다. 정렬은 120바이트 값 대신 8바이트 참조를 옮긴다 | 값 타입과 참조 타입 | 참조 타입, 큰 값의 복사 줄이기, ARC, 힙 객체 | 정렬에서 옮기는 바이트가 줄어 `sortTime`이 줄어든다는 것이 이 처방의 논리다 | 종목마다 힙 객체 하나(객체 헤더 + 할당 단위 올림), 참조를 거칠 때마다 포인터를 따라가야 하고, 참조를 복사할 때 참조 카운트를 늘리고 줄인다. 오히려 느려질 수 있다 | `modelMemory`, `Memory`, `sortTime`, `summaryTime`, `CPU` |
| S2 Advanced | 종목 하나를 객체로 두지 않고 **필드마다 따로 연속 배열**에 둔다 (Struct of Arrays). 정렬은 5만 개의 `Int32` 순번 배열을 제자리에서 줄 세우고, 비교할 때 가격·전일 종가 배열만 읽는다. 순번 배열은 틱마다 새로 만들지 않고 재사용한다 | 메모리 | Struct of Arrays, 캐시 지역성, 할당 재사용, ARC 없는 원소(trivial type) | 정렬과 집계가 필요한 필드만 연속으로 읽어 `sortTime`, `summaryTime`이 줄고, 틱마다의 할당이 사라진다 | 종목 하나를 값 하나로 다룰 수 없다. 필드를 추가하면 배열을 함께 늘려야 하고, 표시용 행을 여러 배열에서 모아 만들어야 한다 | `modelMemory`, `Memory`, 정성: 코드 복잡도와 필드 동기화 |

- 축: 자료구조와 알고리즘, 값 타입과 참조 타입, 메모리, 동시성, 구조, 렌더링, I/O (`docs/GUIDE.md` 3절)
- **세 Stage는 같은 계산을 한다.** 모두 틱마다 id 순서에서 출발해 전체를 정렬하고, 비교할 때마다 등락률을 계산한다.
  직전 순위를 이용해 거의 정렬된 상태에서 시작하거나, 등락률을 미리 계산해 두는 것은 **알고리즘 쪽 처방**이라 이 주제에서는 쓰지 않는다. 메모리 배치의 효과만 남기기 위해서다.
- 모든 Stage는 메인 스레드에서 모델 작업을 한다. 백그라운드로 옮기는 것은 #01에서 다룬 동시성 처방이라 섞지 않는다.
- **S0도 ARC를 치를 수 있다 (추정).** `Stage0Quote`는 값 타입이지만 힙에 있는 문자열(6글자 이상 종목명)을 가리킨다. `sorted(by:)`가 원소를 새 배열로 복사하면
  그 문자열의 참조 카운트를 올리고, 이전 정렬 결과를 버릴 때 내릴 것이다. 그래서 S1의 "참조 카운트 증감" 대가는 S0의 이 비용과 나란히 놓고 본다.
  코드 검증의 Mac 실험(`-O`)에서는 종목명이 모두 힙일 때와 모두 값 안일 때 정렬 시간이 비슷했고, 이전 배열 해제만 약 0.14ms → 0.27ms로 늘었다 (VERIFICATION 0-8).
  측정 단계에서 S0, S1, S2의 `sortQuotes` 구간을 실기기 Time Profiler로 보고 `swift_retain` / `swift_release` 비율을 비교한다.
- **S1의 객체는 한꺼번에 할당된다.** 화면을 열 때 `seeds.map`으로 5만 개를 차례로 만들기 때문에, 힙에서 id 순서로 거의 붙어 놓였을 가능성이 크다 (추정).
  그러면 id 순서로 훑는 집계는 사실상 순차 접근이 되어, 객체가 시간에 걸쳐 흩어져 생기는 실제 앱보다 포인터를 따라가는 대가가 작게 나올 수 있다.
  S1만 불리하게 만들지 않으려고 할당 순서를 일부러 섞지는 않는다. `summaryTime`을 해석할 때 이 한계를 함께 적는다.
  Mac(`-O`)에서는 이웃한 id 객체의 주소 차이가 49,999쌍 중 49,506쌍에서 160B(= `malloc_size`)였다 (VERIFICATION 1-15). iOS 할당기에서는 확인하지 않았다.
  정렬은 id 순서 배열에서 시작하므로 처음 짧은 구간 정렬은 이웃 객체를 차례로 읽고, 병합 단계부터 메모리 순서와 무관하게 읽는다 (추정, 영향의 크기는 재지 않았다).
- **S1에서 실제로 늘어나는 ARC는 반영과 복사에 있다.** Release 목적 파일을 읽어 보니 `applyUpdates`가 종목마다 retain/release를 부르고(S0에는 없다),
  `sorted(by:)`가 새 배열로 참조를 복사하며 retain한다. 정렬 중 원소 이동(`_merge`)은 `memmove`라 retain/release가 없다 (VERIFICATION 1-13, 1-14).
  class `var` 접근의 동적 배타성 검사(`swift_beginAccess`)는 이 Release 빌드(전체 모듈 최적화)의 정렬 코드에서 사라졌다 (1-12). 측정 단계 Time Profiler에서는 `swift_retain` / `swift_release`를 본다.
- `sortTime`에는 정렬만이 아니라 ① 원소를 새 배열로 복사하는 일 ② 이전 정렬 결과를 해제하는 일이 함께 들어간다 (S0, S1의 `sorted(by:)`). S2는 제자리 정렬이라 둘 다 없다.

## 정합성 기준

- Stage마다 모델 로직을 화면과 분리된 타입으로 둔다 (`Stage0QuoteStore`, `Stage1QuoteStore`, `Stage2QuoteStore`). 화면은 이 타입에서 받은 값을 그리기만 한다.
- 테스트에 가장 단순한 기준 구현을 두고, `Scenario.batches`를 **처음부터 끝까지 순서대로** 적용하면서 매 틱 세 Stage의 결과를 비교한다.
  - 순위별 종목 id 배열 전체
  - 집계(상승·하락·보합 수)
  - 몇몇 순위(1등, 중간, 꼴등, 직전 틱에 바뀐 종목)의 표시용 행 값과 깜빡임 방향
- 등락률 동점이 생겨도 id 오름차순으로 순서가 하나로 정해지므로, 정렬 알고리즘의 안정성(같은 값의 원래 순서 유지)에 기대지 않는다.
- `modelMemory`는 Stage마다 계산식이 다르므로, 테스트에서 각 Stage의 값이 0보다 크고 계산식이 쓰는 배열 크기와 맞는지 확인한다.
