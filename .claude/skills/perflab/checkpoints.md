# 체크포인트 (학습 인터럽트)

구현은 Claude가 하지만, 학습은 사용자가 **예측하고, 질문하고, 이해를 확인하는 과정**에서 일어난다.
체크포인트는 그 과정을 강제하는 장치다.

## 원칙

1. **설명보다 질문을 먼저 한다.** 개념을 설명하기 전에 사용자의 예측이나 생각을 먼저 받는다. 답을 듣고 나서 해설한다.
2. **질문은 한 번에 1~3개**로 한다. 짧고 구체적으로 묻는다. 예/아니오로 끝나는 질문은 피한다.
3. **질문하면 턴을 끝낸다.** 답을 받기 전에는 구현이나 문서 작성을 진행하지 않는다.
4. **틀린 답도 그대로 기록한다.** LEARNING.md에 사용자 답변을 원문 그대로 남기고, 해설은 따로 쓴다.
5. **사용자 질문을 환영한다.** 사용자가 되물으면 충분히 답하고, 그 문답도 기록한다. 이해했다고 할 때까지 다음으로 넘어가지 않는다.
6. 사용자가 "넘어가자", "스킵"이라고 하면 그 사실을 기록하고 진행한다. 단, 측정 단계의 예측은 생략하지 않도록 한 번 더 권한다.

## 질문 형식

```
🧠 Checkpoint [<태그>] <주제>

<맥락 1~2줄>

Q1. ...
Q2. ...

(편하게 답해 주세요. 모르겠다면 "모르겠다"도 좋은 답이에요. 궁금한 점이 있으면 같이 질문해 주세요.)
```

## 체크포인트 목록

| 단계 | 태그 | 언제 | 무엇을 묻나 |
|---|---|---|---|
| propose | - | 후보 제시 후 | 어떤 주제로 할지 (결정) |
| plan | `[Plan]` | 계획을 쓰기 **전** | 병목이 어디일 것 같은지, 본인이라면 무엇부터 의심할지 |
| plan | `[Plan]` | 계획을 쓴 **후** | 계획 승인 + 시나리오와 지표가 왜 이렇게 정해졌는지 이해 확인 |
| stageN | `[Stage N]` | 구현 **전** | 이 Stage 전략이 왜 빨라질지 / 무엇을 대가로 치르는지 예측 |
| stageN | `[Stage N]` | 구현 **후** | 핵심 변경을 짚어 주고 이해 확인 질문 1개 + 궁금한 점 |
| measure | `[Measure]` | 결과 공개 **전** | Stage별 핵심 지표 예측 (예: S0→S2 FPS, 메모리 변화 방향) |
| measure | `[Measure]` | 결과 공개 **후** | 예측과 다른 지점에 대해 이유를 함께 추론 |
| summarize | - | 초안 작성 후 | 초안 리뷰, 빠진 내용이나 고칠 표현 |

## 기록 (LEARNING.md)

체크포인트가 끝날 때마다 바로 기록한다.

```markdown
### [Stage 1] 이미지 디코딩을 백그라운드로 옮기면 왜 빨라질까 (2026-10-07)

- **Q.** 메인 스레드에서 이미지를 디코딩하면 스크롤이 왜 끊길까?
- **사용자 답변:** "이미지 크기가 커서 로딩이 오래 걸려서?"
- **해설:** 로딩(I/O)보다 디코딩(압축 해제 → 비트맵)이 핵심이다. ...
- **이해 확인:** 렌더 서버에 넘기기 전 비트맵이 필요하다는 점을 이해했다고 답함
- **남은 궁금증:** 다운샘플링은 디코딩과 어떻게 다른지 → Stage 2에서 다룸
```
