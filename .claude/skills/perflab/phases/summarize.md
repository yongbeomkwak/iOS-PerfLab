# Phase: summarize (measured → summarized)

목표: 주제를 블로그(Tistory)에 올릴 수 있는 글(`docs/SUMMARY.md`)로 정리한다. **덜 쓰고, 핵심은 더 쉽게 쓰고, 그림은 정확할 때만 넣는다.**

## 절차

1. 재료를 모은다: PLAN.md, LEARNING.md, RESULTS.md, VERIFICATION.md, 각 Stage 파일의 전략 주석, 핵심 코드.
   수치는 **실기기 결과**를 쓴다. 실기기 결과가 없으면 사용자에게 알리고, 시뮬레이터 수치에는 "참고용"을 붙인다.
2. **체크포인트 (구성)**: 글을 쓰기 전에 아래 세 가지를 목록으로 보여 주고 확인받는다. 답을 받기 전에는 쓰지 않는다.
   - **뺄 것**: 결론에 쓰이지 않는 지표, 진행 과정, 곁가지 문답
   - **풀어 쓸 것**: 이 글의 핵심 개념 2~3개와 각각에 쓸 비유
   - **그림**: 넣을 차트(지표 이름), 다이어그램(무엇을 보여 주는지), 화면 캡처. 각각 왜 글보다 그림이 나은지 한 줄
3. 그림을 만든다 (`.claude/rules/docs.md` "그림").
   - 차트: `scripts/perflab chart <topic> --metric <이름>`. 숫자를 직접 옮겨 적은 차트는 만들지 않는다.
   - 다이어그램: `docs/assets/diagram-<이름>.svg`를 쓰고 `scripts/perflab png <topic>`으로 PNG를 만든다.
   - 만든 PNG를 직접 열어 글자가 겹치거나 잘리지 않았는지 확인한다.
4. `docs/SUMMARY.md` 템플릿을 채운다 (`.claude/rules/docs.md` 준수).
   - **단계별 구현**: Stage마다 핵심 코드 스니펫 1개 이하를 넣는다. 전체 코드는 레포 링크로 대신한다.
   - **측정 결과**: 결론을 뒷받침하는 지표만 넣는다. 기기와 빌드 구성을 명시한다. 전체 표는 RESULTS.md 링크로 대신한다.
   - **필요한 CS 지식**: 핵심 개념 2~3개를 비유로 풀고, 비유마다 한계를 한 줄 붙인다. 나머지 개념은 1~2문장으로 줄인다.
   - **예측과 실제**: LEARNING.md의 사용자 예측을 근거로 쓴다. 가장 크게 빗나간 것 위주로 고른다.
   - **트레이드오프 & 회고**: 실무에서는 어느 Stage까지 적용할지 판단 기준을 남긴다.
5. **글 검토**: `summary-reviewer` 에이전트에 주제 경로를 넘긴다.
   - 보고를 `docs/VERIFICATION.md`에 `### [Summary]`로 붙이고, ⚠️/❌를 조치해 `조치` 열에 적는다.
   - 편집 제안(뺄 것, 더 쉽게 풀 것, 그림)은 반영하거나, 반영하지 않은 이유를 사용자에게 알린다.
   - 글을 크게 고쳤으면 다시 검토받는다.
6. **체크포인트 (리뷰)**: 초안을 보여주고 묻는다.
   - 빠진 내용, 고칠 표현, 비유가 와닿는지, 그림이 도움이 되는지
   - 마지막 확인 질문: "이 주제를 한 문장으로 설명한다면?" → 사용자 답을 SUMMARY의 한 줄 요약 후보로 쓴다.
7. 피드백을 반영하고 `scripts/perflab advance <topic>` 후 종료 보고하고 멈춘다.
   종료 보고에 Tistory에 올릴 때 함께 업로드할 PNG 목록(글에 나오는 순서)을 적는다.

## 주의

- 재료가 많다고 글이 좋아지지 않는다. LEARNING.md와 RESULTS.md에 있는 내용을 모두 옮기지 않는다. 독자가 얻어 갈 것 2~3가지를 먼저 정하고, 거기에 쓰이지 않는 것은 뺀다.
- 그림이 글보다 복잡하면 넣지 않는다. 그림이 없는 글이 틀린 그림이 있는 글보다 낫다.
- Tistory는 Mermaid와 SVG를 그리지 못한다. 글에는 PNG만 넣는다 (SVG는 원본으로 보관한다).
