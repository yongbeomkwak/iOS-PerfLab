# Phase: plan (proposed → planned)

목표: 공정하고 재현 가능한 실험을 설계한다. 이후 모든 Stage는 이 계획을 기준으로 구현된다.

## 절차

1. **체크포인트 `[Plan]` (계획 전)**: 상황과 요구사항만 설명하고 묻는다.
   - 이 화면에서 병목은 어디일 것 같은가?
   - 본인이 이 기능을 처음 만든다면 어떻게 만들었을까? (= Stage 0 후보)
   - 답을 받기 전에는 계획을 쓰지 않는다.
2. 답을 반영해 `docs/PLAN.md`를 작성한다.
   - **사용자 예측** 섹션에는 사용자 답을 그대로 옮긴다.
   - **시나리오**: 데이터 규모와 갱신 주기는 Stage 0에서 병목이 **분명히 드러나는** 수준으로 정한다. 근거를 적는다.
   - **Benchmark 모드 자동 재생 방식**: 사용자 입력 없이 부하를 만드는 방법 (자동 스크롤 속도, 타이머 주기 등)
   - **측정 지표**: 공통 지표 외에 이 주제의 핵심 지표가 있으면 커스텀 지표로 정의한다.
   - **Stage 전략**: Stage마다 핵심 개념 하나에 집중하고, 어느 최적화 축(`docs/GUIDE.md` 3절)의 어떤 CS 개념인지 적는다.
     Stage 2는 저수준 API에 한정하지 않는다. Stage 1이 남긴 근본 원인을 가장 잘 공략하는 축을 고른다.
   - **대가와 대가 지표**: Stage마다 무엇을 대가로 치르는지(메모리, CPU, 지연 등) 적고, **잴 수 있는 대가는 반드시 지표로 잰다.**
     공통 지표로 부족하면 커스텀 지표를 추가한다 (예: 캐시나 인덱스의 메모리). 커스텀 대가 지표는 모든 Stage가 기록한다 (해당 구조가 없으면 0).
     `scripts/perflab advance`가 대가 지표 열이 비었거나 정의되지 않은 지표를 쓰면 실패한다.
   - **정합성 기준**: Stage 간 결과가 같다는 것을 테스트로 어떻게 확인할지 적는다.
3. `Scenario.swift`에 시나리오(데이터 생성, 파라미터)를 구현하고 TODO를 지운다. 데이터는 반드시 `Scenario.makeGenerator()`로 만든다.
4. `Tests/`에 시나리오 결정성 테스트를 보강한다.
5. **체크포인트 `[Plan]` (계획 후)**: 계획 요약을 보여주고 묻는다.
   - 계획을 승인하는지, 바꾸고 싶은 점이 있는지
   - 이해 확인 질문 1개 (예: "데이터를 왜 N개로 정했을까?")
6. LEARNING.md에 `### [Plan]` 기록을 남긴다.
7. 검증 및 전환:

   ```bash
   scripts/perflab test <topic>
   scripts/perflab advance <topic>
   ```

8. 종료 보고 후 멈춘다.
